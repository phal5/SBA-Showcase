## 결점

### 1. `DropReason.MalformedDatagram`의 주석과 실제 반환 경로의 모순
- **유형**: 자기모순
- **어디**:
  - `src/Realtime.Assembly/Stubs/DropReason.cs:39`
  - `src/Realtime.Assembly/Stubs/DropReason.cs:69` (대응 항목 `InboundDatagramTooLarge`)
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:121-125`
- **무엇이 어긋나는가**:
  `DropReason.cs:39`의 `MalformedDatagram` 주석에는 `(너무 짧거나 경로 상한을 넘는다)`라고 설명되어 있으나, 비대칭 경로 상한 도입(D5) 이후 데이터그램이 수신 상한을 초과하는 경우는 `DropReason.InboundDatagramTooLarge`로 완전히 분리되었다(`DropReason.cs:63-69`, `ASYMMETRY-NOTES.md:28, 68`).
  실제 `DatagramOpener.TryOpen`에서도 데이터그램 길이가 수신 상한을 넘으면 `InboundDatagramTooLarge`를 반환하며(`DatagramOpener.cs:123`), `MalformedDatagram`은 데이터그램 길이가 헤더/오버헤드보다 짧아 배치가 깨진 경우에만 반환된다(`DatagramOpener.cs:113`). 따라서 `MalformedDatagram`의 주석에 남아 있는 `경로 상한을 넘는다`라는 설명은 실제 코드 동작 및 `InboundDatagramTooLarge`의 정의와 모순된다.
- **재현 방법**:
  `DatagramOpener` 인스턴스(수신 상한 1,200 B)에 1,201 B 길이의 유효하게 봉인된 데이터그램을 `TryOpen`에 전달하면, 반환되는 `reason`은 주석에 명시된 `MalformedDatagram`이 아니라 `InboundDatagramTooLarge`이다.
- **확신도**: 확신

### 2. `EngineOptions.Validate()`의 $N_{conn}$ 불변식 오류 메시지 논리 역전
- **유형**: 자기모순
- **어디**:
  - `src/Realtime.Assembly/Stubs/EngineOptions.cs:254`
  - `src/Realtime.Assembly/Stubs/EngineOptions.cs:256-259`
- **무엇이 어긋나는가**:
  `EngineOptions.cs:256`의 불변식 `PerConnectionReassemblyContexts <= PerConnectionReassemblyBytes / ContextOverheadBytes` ($N_{conn} \le \lfloor B_{conn}/A_{ctx} \rfloor$)는 건수 축 상한이 바이트 축 상한보다 커서 건수 축에 결코 도달하지 못하는(바이트 축이 먼저 고갈되어 건수 축이 무의미해지는) 상황을 방지하기 위한 검사이다(254행 주석: `건수 축이 바이트 축을 무의미하게 만들지 않을 것 (R10.4 / 계획 K12)`).
  그러나 검사 실패 시 출력되는 예외 메시지(259행)는 `$"N_conn({PerConnectionReassemblyContexts}) > ⌊B_conn/A_ctx⌋(...) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."`로 작성되어 있다.
  실제로는 $N_{conn} \le \lfloor B_{conn}/A_{ctx} \rfloor$일 때 작은 메시지가 다수 수신되면 건수 축이 바이트 축보다 먼저 걸릴 수 있고(하네스 검사 6-(b)에서 이를 검증), $N_{conn} > \lfloor B_{conn}/A_{ctx} \rfloor$가 되었을 때의 실제 문제 현상은 **"바이트 축이 항상 먼저 걸려 건수 축에 도달할 수 없다"**이다. 예외 메시지의 인과 설명 문장이 거꾸로 서술되어 있어 코드의 본래 검사 의도 및 254행의 주석과 모순된다.
- **재현 방법**:
  `new EngineOptions { PerConnectionReassemblyBytes = 1000, ContextOverheadBytes = 128, PerConnectionReassemblyContexts = 10 }.Validate()`를 호출하면 `ArgumentException`이 발생하며 메시지에 `"N_conn(10) > ⌊B_conn/A_ctx⌋(7) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."`가 출력된다. 하지만 실제 상황은 최소 부기 비용 $10 \times 128 = 1280 > 1000$으로 인해 바이트 축이 먼저 걸려 10건(건수 축)에 도달할 수 없는 상태이다.
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`ReassemblyTable.Offer`의 `slot < 0` 방어 분기 (`ReassemblyTable.cs:118-126`)**:
   `_budget.TryReserve`에서 이미 건수 축($N_{conn}$)을 검사하므로 슬롯 배열(`_slots.Length == N_conn`)에 빈자리가 없는 상황은 단일 스레드 환경에서 도달 불가능하다. 그러나 주석에서 `// 건수 축이 슬롯 수와 같으므로 도달 불가. 조용히 넘치는 대신 회수하고 거절한다.`라고 명시하고 자원을 안전하게 회수한 후 거절하는 방어적 프로그래밍(Defensive Guard)이므로 결점이 아니다.

2. **`MessageSplitter.TryPlan`의 `totalFragments > MaxFragmentsPerMessage` 분기 (`MessageSplitter.cs:128-134`)**:
   `EngineOptions.Validate()` 및 `PathLimits` 생성자에서 K4와 방향별 관계 검증(D6/D10)을 수행하므로 정상 설정에서는 도달할 수 없다. 그러나 설정이 동적으로 변하거나 비정상적인 입력이 들어올 때 조용히 오버플로되는 것을 막기 위한 방어적 가드로 남겨둔 것이며, 주석에도 의도가 명시되어 있으므로 결점이 아니다.
