## 결점

### 1. `ReassemblyDeliveryPipeline.DrainToApplication`에서 슬롯 일치 여부 확인 시 `ConnectionTag`를 검사하지 않음
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:51` 및 `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:10-15`
- **무엇이 어긋나는가**: `DEVIATIONS.md` 40행 및 코드베이스 전반에서 `ReassemblyId`는 연결별(Per-connection) 식별자이며 고유 열쇠는 `(ConnectionTag, ReassemblyId)` 쌍이라고 명시하고 있습니다. `DeferredReassemblyDeliveryRecord` 구조체에도 `ConnectionTag` 필드가 저장되어 있습니다. 그러나 지연 큐를 비우는 `ReassemblyDeliveryPipeline.DrainToApplication`의 51행에서는 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag != work.ConnectionTag`를 검사하지 않습니다. 이로 인해 연결 A의 완료 작업이 큐에 쌓인 상태에서 연결 A가 회수되고, 그 슬롯 인덱스를 연결 B가 같은 `ReassemblyId`로 재사용할 경우, 연결 A의 지연 작업이 연결 B의 슬롯을 대상으로 실행되어 연결 B의 슬롯을 조기 전달 및 반납(해제)해 버립니다.
- **재현 방법**:
  1. 연결 `0xAA`에서 `ReassemblyId = 1`인 메시지를 완성하여 완료 판정을 받음 (슬롯 0 할당, `DeferredReassemblyDeliveryRecord(SlotIndex=0, ConnectionTag=0xAA, ReassemblyId=1)`가 지연 큐에 진입). 이때 `Poll`을 호출하지 않아 `DrainToApplication`이 아직 실행되지 않은 상태로 둠.
  2. `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0xAA)`를 호출하여 연결 `0xAA`를 회수함 (슬롯 0이 반납되어 자유 목록에 들어감).
  3. 연결 `0xBB`에서 `ReassemblyId = 1`인 메시지를 전송하여 슬롯 0을 새로 할당받고 완성시킴.
  4. 이제 `world.Poll(...)`을 실행하여 `DrainToApplication`을 진입시킴.
  5. 큐에 있던 0xAA의 지연 항목이 슬롯 0을 확인할 때 `slot.ReassemblyId == 1` 조건이 참이 되어 연결 0xBB의 슬롯 0을 배달하고 해제(`_arena.Release(slot)`, `_pool.Return(lease)`)함. 이후 0xBB의 지연 항목이 실행될 때는 슬롯이 이미 Free 상태여서 무시됨.
- **확신도**: 확신

### 2. `ReassemblyProgressRecord.IsComplete`가 기본값(`default`)에서 `true`를 반환하여 완성 불변식이 우회됨
- **유형**: 계산 오류
- **어디**: `src/Assembly/Records/ReassemblyProgressRecord.cs:25` 및 `src/Assembly/Records/ReassembledMessageRecord.cs:57`
- **무엇이 어긋나는가**: `ReassemblyProgressRecord` 생성자(16행)는 `fragmentCount <= 0`에 대해 예외를 던지도록 방어하지만, 구조체 기본값인 `default(ReassemblyProgressRecord)`는 `ArrivedFragmentCount = 0`, `FragmentCount = 0`을 가집니다. 25행의 `IsComplete` 프로퍼티는 `ArrivedFragmentCount == FragmentCount`로 구현되어 있어 `0 == 0`이 `true`로 평가됩니다. 이로 인해 `ReassembledMessageRecord.cs` 주석(8~12행)에서 "완성 판정(`IsComplete == true`) 없이는 생성될 수 없다"고 선언한 불변식이 `ReassembledMessageRecord.TryCreate(default, ...)` 호출 시 통과되어 0조각짜리 빈 메시지 레코드가 생성됩니다.
- **재현 방법**:
  ```csharp
  var progress = default(ReassemblyProgressRecord);
  // progress.IsComplete는 true를 반환함
  bool created = ReassembledMessageRecord.TryCreate(
      progress, pool, lease, tag: 0x1, reassemblyId: 1, lengthBytes: 0, out var message);
  // created는 true가 되고 message는 유효한 인스턴스로 생성됨
  ```
- **확신도**: 확신

### 3. `DatagramOpenPipeline.OpenDatagram`에서 2단계 머리말 파싱 실패 분기가 도달 불가능함
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96`
- **무엇이 어긋나는가**: 1단계(68행)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes` (53) 조건을 검사하여 이미 거절합니다. 2단계(93행)의 `SealedDatagramHeaderRecord.TryParse`는 `source.Length < WireBytes` (24)일 때만 `false`를 반환합니다. 이미 1단계에서 길이가 53 이상임이 보장되므로 `TryParse`는 항상 `true`를 반환하며, 93~96행의 `if (!SealedDatagramHeaderRecord.TryParse(...))` 실패 분기는 절대로 실행되지 않는 죽은 코드입니다.
- **재현 방법**: `datagram.Length`가 24 미만인 데이터그램은 68행의 최소 길이(53 B) 검사에서 먼저 걸려 `Refuse`로 반환되므로, 93행의 조건문이 거짓이 되어 `Refuse`를 호출하는 경우는 발생할 수 없습니다.
- **확신도**: 확신
