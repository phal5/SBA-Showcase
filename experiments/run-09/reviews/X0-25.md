### 1. `DropReason.MalformedDatagram`의 주석이 경로 상한 분리 구현과 모순됨

- **어디**:
  - `src/Realtime.Assembly/Stubs/DropReason.cs:40`
  - `src/Realtime.Assembly/Stubs/DropReason.cs:64-70`
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:121-125`
  - `ASYMMETRY-NOTES.md:28, 68`
- **무엇이 어긋나는가**: `DropReason.cs:40`의 `MalformedDatagram` 요약 주석은 `"(너무 짧거나 경로 상한을 넘는다)"`라고 기술하고 있습니다. 그러나 방향별 경로 상한 도입(D5) 이후, 경로 상한을 넘는 데이터그램은 `InboundDatagramTooLarge`(15)로 분리되어 `DatagramOpener.cs:121-125`에서 처리되며, `MalformedDatagram`(9)은 오직 바이트 배치/최소 길이 부족 시에만 발생합니다. `DropReason.cs:66-68`의 `InboundDatagramTooLarge` 주석 및 `ASYMMETRY-NOTES.md:28, 68`에서도 두 사유를 분리했다고 명시하고 있으나, `DropReason.cs:40`의 기존 주석은 갱신되지 않고 남아 모순됩니다.
- **재현 방법**:
  1. 들어오는 쪽 상한이 1,200 B인 연결(`PathLimits(options, 1452, 1200)`)에 1,201 B 크기의 유효하게 봉인된 데이터그램을 수신 경로(`DatagramOpener.TryOpen` 또는 `SealedDatagramIntake.Offer`)로 전달합니다.
  2. `DropReason.InboundDatagramTooLarge`(15)가 반환되며, `MalformedDatagram`(9) 계수는 증가하지 않습니다 (`Program.cs` 검사 18-(d)에서도 `MalformedDatagram == 0`임을 확인).
  3. `DropReason.MalformedDatagram`은 데이터그램 길이가 경로 상한을 넘는 상황에서 결코 산출되지 않으므로, `DropReason.cs:40`의 주석 내용과 실제 동작이 불일치합니다.
- **확신도**: 확신

### 2. `EngineOptions.Validate()`의 건수 축 불변식(K12) 예외 메시지 인과관계 역전
- **유형**: 자기모순 / 계산 오류
- **어디**:
  - `src/Realtime.Assembly/Stubs/EngineOptions.cs:256-259`
  - `harness/Program.cs:602-626`
- **무엇이 어긋나는가**: `EngineOptions.cs:258-259`에서 `N_conn <= ⌊B_conn/A_ctx⌋` 불변식을 검사할 때, 조건 위반 시 `$"N_conn({PerConnectionReassemblyContexts}) > ⌊B_conn/A_ctx⌋({PerConnectionReassemblyBytes / ContextOverheadBytes}) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."`라는 예외 메시지를 출력합니다.
  그러나 `N_conn > ⌊B_conn/A_ctx⌋`가 금지되는 실제 수학적 이유는, 건당 최소 부기 비용(`A_ctx`)으로 인해 `N_conn` 건수에 도달하기 전에 바이트 예산(`B_conn`)이 항상 먼저 소진되어 **"바이트 축이 건수 축보다 항상 먼저 걸려 건수 축이 무의미해지기(건수 축에 결코 도달할 수 없기)"** 때문입니다.
  반대로 정상 설정(`N_conn <= ⌊B_conn/A_ctx⌋`)에서는 작은 메시지들이 유입될 때 **"건수 축이 바이트 축보다 먼저 걸리는 것"**이 정상적이고 의도된 핵심 동작이며, `Program.cs` 검사 6(b)(618행: `if (t2.Budget.Bytes >= o.PerConnectionReassemblyBytes) return "건수 축이 아니라 바이트 축이 먼저 걸렸다"`)에서도 건수 축이 바이트 축보다 먼저 걸려야 함을 엄격히 단언합니다. 따라서 예외 메시지의 서술은 불변식의 수학적 의미 및 시스템의 의도된 동작과 정반대로 작성되어 있습니다.
- **재현 방법**:
  1. `new EngineOptions { PerConnectionReassemblyBytes = 1000, ContextOverheadBytes = 128, PerConnectionReassemblyContexts = 10 }.Validate()`를 호출합니다 (`N_conn = 10 > ⌊1000/128⌋ = 7`).
  2. `ArgumentException`이 발생하며 `"설정 오류 [PerConnectionReassemblyContexts]: N_conn(10) > ⌊B_conn/A_ctx⌋(7) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."` 메시지가 출력됩니다.
  3. 실제로는 128 B짜리 최소 컨텍스트가 7개만 열려도 896 B가 되어 8번째에서 1000 B(B_conn)를 초과하므로, 바이트 축이 먼저 걸려 10건(건수 축)에 결코 도달할 수 없는 상황임에도 메시지는 반대로 설명합니다.
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`SealedDatagramIntake.Offer`의 `out DropReason reason`이 표(Table) 거절 시 `None`인 동작**
   - `SealedDatagramIntake.Offer`는 개봉 실패 시 `reason`을 채우고, 성공 시 `DropReason.None`으로 설정한 뒤 `_table.Offer`를 호출합니다. `ReassemblyTable.Offer`는 거절 사유를 내부 `CounterBank`에 직접 집계하고 `FragmentAdmission`만 반환합니다. `SealedDatagramIntake`의 XML 주석에서도 `reason` 파라미터는 "열리지 않을 때(`SealRejected`)" 사유를 담고 열린 뒤의 판정은 D7의 것이라고 명시하고 있으므로 설계 의도에 부합합니다.

2. **`ReassemblyTable.Offer` 내 `FreeSlot() < 0` 방어 분기**
   - `_slots` 배열 크기가 `PerConnectionReassemblyContexts`와 같고, 앞서 `_budget.TryReserve`에서 건수 상한을 검증하므로 정상 상태에서 `FreeSlot() < 0` 분기는 도달 불가능(dead code)합니다. 그러나 이는 내부 상태 불일치를 대비한 방어적 프로그래밍(defensive check)으로, 자원 누수 없이 대여한 버퍼와 예산을 회수하고 거절하므로 결함이 아닙니다.

3. **`DatagramOpener.TryOpen`의 `plaintext.Length < bodyLength` 시 예외 발생**
   - E3 원칙("예외를 던지지 않는다")은 수신된 와이어 바이트의 훼손/변조에 대한 것이며, 호출자가 제공한 버퍼 크기 부족은 호출 측의 프로그래밍 오류(API 규약 위반)이므로 `ArgumentException`을 던지는 것은 정상입니다. 또한 `SealedDatagramIntake`는 생성 시 `limits.Inbound` 크기로 버퍼를 할당하므로 이 예외에 도달하지 않습니다.

4. **`MaxFragmentsPerMessage (F = 64)`의 도달 불가능 여유 (59~64조각)**
   - `DEVIATIONS.md` 및 `Program.cs` 검사 2에서 이미 상세히 분석하고 명시한 기지의 사실(비어 있는 값역)이며, 비트맵 크기(64비트)와 부등식 K4를 만족하므로 무해합니다.

5. **`ASYMMETRY-NOTES.md` 및 `EXTENSION-NOTES.md` §5에 기재된 남은 결함들**
   - `PathLimits`의 스레드 비안전성, `MaxInboundFragments`가 `D_floor` 기준으로 산출되는 점, `Promote` 시 이전 시대 창 소멸 등은 문서에서 명시적으로 트레이드오프와 가정을 밝힌 항목들입니다.
