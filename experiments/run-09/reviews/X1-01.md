### 1. `ReassemblyExpirySweepPipeline`이 완료되어 배달 대기 중인 슬롯을 마감 초과로 회수하여 메시지가 유실되는 결함
- **유형**: 자기모순 / 자원 누수
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyExpirySweepPipeline.cs:44-50`
  - `harness/Program.cs:1648-1652`
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50`
- **무엇이 어긋나는가**:
  - 주석(`ReassemblyExpirySweepPipeline.cs:9`) 및 명세 R4.2는 *"what is left unfinished is reclaimed once enough time has passed"* 라며 미완성 상태로 남겨진 재조립 슬롯만을 회수 대상으로 규정합니다. 또한 `DEVIATIONS.md` 이탈 #5는 완성이 완료된 후의 슬롯 반납 책임을 트리거가 아닌 `ReassemblyDeliveryPipeline`이 애플리케이션 전달 완료 후에 수행하도록 명시합니다.
  - 그러나 `ReassemblyExpirySweepPipeline.SweepExpired()`는 슬롯이 이미 조립 완료(`IsComplete == true`)되어 `_deferredWork` 큐에 적립된 상태인지 확인하지 않고, `_arena.OpenSlots()` 전체를 순회하며 마감 시각(`DeadlineTick`)만 지나면 즉시 슬롯을 회수(`Release`)하고 버퍼를 풀에 반납(`_pool.Return`)해 버립니다.
  - 더 나아가 `AssemblyWorld.Poll()`에서 `Sweep.SweepExpired()`가 `Delivery.DrainToApplication(Sink)`보다 **먼저** 실행되므로, 마감 시각(`firstFragmentTick + 20,000 ms`)과 동일하거나 늦은 틱에 `Poll`이 호출되면 직전에 조립 완료된 메시지가 애플리케이션으로 배달되기 전에 `Sweep`에 의해 파괴됩니다. 이후 실행되는 `DrainToApplication`에서는 `slot.State != ReassemblySlotState.Open` 조건에 걸려 메시지를 버리고 건너뛰므로 애플리케이션 배달이 영구 유실됩니다.
- **재현 방법**:
  1. 틱 1,000에 2조각짜리 메시지(길이 2,000 B, 태그 `0xA1`, ReassemblyId `1`)의 조각 0을 수신합니다. 슬롯의 `DeadlineTick`은 21,000으로 설정됩니다.
  2. 틱 20,900에 조각 1을 수신합니다. 모든 조각이 도착하여 `AcceptFragmentCarrier`가 완료 판정 및 `FileDelivery`를 호출하여 `_deferredWork`에 배달 작업을 적립합니다 (슬롯 상태는 여전히 `Open`).
  3. 틱 21,000에 `world.Poll(21_000)`을 호출합니다.
  4. `Poll` 내부에서 `Sweep.SweepExpired()`가 먼저 실행되어 틱 21,000에 마감된 해당 슬롯을 `Expired`로 처리하고 강제 `Release` 및 버퍼를 반납합니다.
  5. 직후 `Delivery.DrainToApplication(Sink)`가 실행되지만 `slot.State`가 `Free`이므로 전달을 건너뜁니다.
  6. 결과: `world.Sink.Deliveries.Count`는 0이며 정상 완료된 메시지가 전달되지 않고 유실됩니다.
- **확신도**: 확신

### 2. `ReassemblyDeliveryPipeline.DrainToApplication`에서 슬롯 재사용 검증 시 `ConnectionTag` 불일치를 확인하지 않는 결함
- **유형**: 미강제 불변식 / 자기모순
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:49-52`
  - `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:8-24`
- **무엇이 어긋나는가**:
  - `DeferredReassemblyDeliveryRecord`는 지연 배달 시 슬롯이 다른 용도로 재사용되었는지 엄밀히 식별하기 위해 `SlotIndex`뿐만 아니라 `ConnectionTag`와 `ReassemblyId`를 모두 값으로 보관합니다 (`DEVIATIONS.md` 40행에서 `ReassemblyId`는 전역이 아닌 연결별 식별자이므로 서로 다른 연결 간에 동일한 `ReassemblyId`가 존재할 수 있음).
  - 그러나 `ReassemblyDeliveryPipeline.DrainToApplication`의 슬롯 재사용 검사 로직(50-51행)은 다음과 같습니다:
    ```csharp
    var slot = _arena.SlotAt(work.SlotIndex);
    if (slot.State != ReassemblySlotState.Open) continue;      // already reclaimed
    if (slot.ReassemblyId != work.ReassemblyId) continue;      // the slot was reused
    ```
    여기서 `slot.ConnectionTag == work.ConnectionTag`를 검사하지 않습니다.
  - 따라서 이전 연결 A의 완료 작업이 큐에 남아 있는 상태에서 연결 A가 회수되고, 동일한 슬롯 인덱스에 연결 B가 동일한 `ReassemblyId`(예: 1)로 새 슬롯을 열어 사용 중인 경우, `slot.ReassemblyId == work.ReassemblyId`가 참이 되어 검증을 통과해 버립니다. 이로 인해 연결 B의 미완성 상태를 평가하거나 연결 B의 슬롯을 조기 회수(`Release`)하는 오동작이 발생합니다.
- **재현 방법**:
  1. 연결 A(Tag `0xA1`)에서 `ReassemblyId = 1` 메시지가 완성되어 `FileDelivery`로 큐에 적립됩니다 (SlotIndex `0`, ConnectionTag `0xA1`, ReassemblyId `1`).
  2. `Poll`이 돌기 전에 연결 A가 종료되어 `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0xA1)`을 호출합니다 (Slot 0이 회수되어 `Free`가 됨).
  3. 즉시 새로운 연결 B(Tag `0xB1`)가 데이터그램을 수신하여 Slot 0을 할당받고 `ReassemblyId = 1`로 슬롯을 엽니다.
  4. `Delivery.DrainToApplication`이 실행되면 큐에서 연결 A의 작업 항목을 꺼내 Slot 0을 검사합니다.
  5. Slot 0은 `State == Open`이고 `ReassemblyId == 1`이므로 50-51행의 검사를 그대로 통과하며, `work.ConnectionTag (0xA1)`와 `slot.ConnectionTag (0xB1)`가 불일치함에도 걸러내지 못합니다.
- **확신도**: 확신

### 3. `FragmentOffsetBoundsFragment.Evaluate`의 `offset + expected > total` 조건이 항상 거짓인 죽은 코드
- **유형**: 도달 불가능한 갈래 / 죽은 코드
- **어디**:
  - `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:49-58`
- **무엇이 어긋나는가**:
  - `FragmentationHeaderRecord.ExpectedPayloadLengthBytes`는 다음과 같이 계산됩니다:
    ```csharp
    int uniform = UniformFragmentPayloadBytes;
    int offset = FragmentIndex * uniform;
    int remaining = (int)TotalLengthBytes - offset;
    return remaining < uniform ? remaining : uniform;
    ```
  - `FragmentOffsetBoundsFragment.Evaluate` 43행에서 `offset >= total`을 먼저 거절하므로 이후 단계에서 `remaining = total - offset > 0`입니다.
  - `ExpectedPayloadLengthBytes`는 정의상 `min(uniform, total - offset)`이므로 항상 `expected <= total - offset`입니다.
  - 양변에 `offset`을 더하면 항상 `offset + expected <= total`이 성립합니다.
  - 따라서 54행의 `if (offset + expected > total)` 조건은 수학적으로 절대 참이 될 수 없으며, 그 안의 `Reject(DropReason.FragmentOffsetOutOfBounds)`는 영원히 도달할 수 없는 죽은 코드입니다.
- **재현 방법**:
  - 임의의 `TotalLengthBytes`, `FragmentCount`, `FragmentIndex` 조합을 생성하여 43행(`offset >= total`)과 49행(`arrivedPayloadLengthBytes != expected`)을 통과시키더라도, 54행 `offset + expected > total`이 `true`가 되는 입력은 수학적으로 구성할 수 없습니다.
- **확신도**: 확신

  - `src/Security/Records/SealedDatagramHeaderRecord.cs:62-73`

  - 2단계(93행)의 `SealedDatagramHeaderRecord.TryParse(datagram, out var header)`는 `source.Length < WireBytes` (24 B)인 경우에만 `false`를 반환하도록 작성되어 있습니다.

### 5. `SealedDatagramSendPipeline.WriteSealedFragmentDatagram`에서 유효하지 않은 `fragmentIndex` 입력 시 예외를 던지는 결함
- **유형**: 미강제 불변식 / 자기모순
- **어디**:
  - `src/Security/Pipelines/SealedDatagramSendPipeline.cs:77-78`
  - `src/Assembly/Pipelines/MessageFragmentationPipeline.cs:69-83`
  - `src/Assembly/Records/MessageSplitPlanRecord.cs:33-37`
- **무엇이 어긋나는가**:
  - `SealedDatagramSendPipeline.WriteSealedFragmentDatagram`의 문서 주석(64행)은 엔진 파이프라인의 핵심 규약에 따라 예외를 던지지 않고 거절 평결(`Verdict<int>.Reject`) 또는 바이트 수를 반환한다고 명시합니다.
  - 그러나 1단계에서 `MessageFragmentationPipeline.WriteFragmentCarrier`를 호출하기 전 `fragmentIndex`의 범위(`0 <= fragmentIndex < plan.FragmentCount`)를 전혀 검사하지 않습니다.
  - `WriteFragmentCarrier` 내에서 `plan.OffsetOf(fragmentIndex)`와 `plan.LengthOf(fragmentIndex)`를 계산하여 `message.Slice(offset, length)`를 호출하는데, `fragmentIndex >= plan.FragmentCount`이거나 음수인 경우 `length`가 음수가 되거나 `offset`이 `message.Length`를 초과하여 `ArgumentOutOfRangeException` 예외가 발생하며 파이프라인 외부로 던져집니다.
- **재현 방법**:
  1. `plan = fragmentation.PlanSplit(1000, tag)`로 1조각 계획 생성 (`FragmentCount = 1`).
  2. `world.Seal.WriteSealedFragmentDatagram(tag, plan.Value, reassemblyId: 1, fragmentIndex: 5, message, datagram)` 호출 (`fragmentIndex = 5`는 `FragmentCount = 1`을 초과).
  3. `MessageFragmentationPipeline.WriteFragmentCarrier`에서 `offset = 5000`으로 계산되어 `message.Slice(5000, ...)` 호출 시 `ArgumentOutOfRangeException` 예외 발생.

## 결점이 아니라고 판단한 것

1. **`DEVIATIONS.md` 산문에 남아 있는 확장 이전 수치 (1,182, 1,402, 65,664 등)**
   - `DEVIATIONS.md` 서두(3-6행) 및 `EXTENSION-NOTES.md` §3, §5.1, `ASYMMETRY-NOTES.md` §5.7에서 해당 수치들이 보안 확장 및 비대칭 지원 이전 시점의 설계 판단 기록으로서 의도적으로 보존되었음을 명확히 밝히고 있습니다. 최신 수치의 변경 이력과 사유가 후속 문서들에 온전히 기록되어 있으므로 결함이 아닌 의도된 설계 이력 보존으로 판단했습니다.

2. **`EngineConstantsRecord.FindViolatedConstantRelation()` 내 상수 비교 (`MaxMessageBytes > uint.MaxValue` 등)**
   - `FindViolatedConstantRelation()` 내부의 분기들 중 상수를 직접 비교하는 식(예: 65,536 > uint.MaxValue)은 컴파일러에 의해 접혀(fold) 도달할 수 없는 코드로 판정되나, 209-217행에 `#pragma warning disable CS0162`와 함께 컴파일 타임 검증 및 값 변경 시 재검증을 목적으로 둔 것임이 명시되어 있으므로 죽은 코드가 아닌 정적 단언(static assertion) 메커니즘으로 판단했습니다.

3. **`FragmentReceivePipeline.OpenSlot`의 `slot is null` 검사 분기**
   - 182행의 `ReassemblyAdmissionFragment.Evaluate`가 전체 슬롯 예산(`total.RemainingSlots < 1`)을 사전에 검증하므로 191행의 `_arena.Reserve`는 항상 슬롯을 성공적으로 반환하며 `null`이 될 수 없습니다. 그러나 이는 리소스 예약 실패에 대비한 계층 간의 표준적인 방어적 프로그래밍(defensive programming)으로 판단했습니다.

4. **`SealedFragmentReceivePipeline`의 `_sealedAreaScratch` 버퍼 즉시 미초기화**
   - 데이터그램 수신 후 평문 스크래치 버퍼를 매번 0으로 초기화하지 않지만, 열기 실패 시에는 `DatagramOpenPipeline` 153행에서 `Clear`가 수행되고, 정상 경로에서는 다음 수신된 바이트로 즉시 덮어쓰여지며 힙 할당을 0으로 유지하기 위한 의도된 재사용 버퍼(E10)이므로 자원 누수나 보안 결함이 아니라고 판단했습니다.
