## 결점

### 1. ReassemblyDeliveryPipeline의 슬롯 재사용 검증 시 ConnectionTag 불일치 누락
- **유형**: 미강제 불변식 / 자기모순
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50-51`
  - `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:49-50`
  - `DEVIATIONS.md:39-43`
- **무엇이 어긋나는가**:
  - `DEVIATIONS.md` §"계획이 답을 주지 못한 지점" (39~43행)에서 `ReassemblyId`는 연결별(per-connection)로 스코프가 지정되며, 색인 열쇠는 `(연결 태그, ReassemblyId)`의 쌍으로 고정되었습니다. `ReassemblyArenaResource` 역시 `(ulong Tag, uint ReassemblyId)`를 슬롯 색인 키로 사용합니다.
  - `ReassemblyCompletionTrigger.FileDelivery`는 지연 작업 큐에 `DeferredReassemblyDeliveryRecord`를 적립할 때 `slot.ConnectionTag`를 함께 기록합니다(`ReassemblyCompletionTrigger.cs:49-50`).
  - 그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 큐에서 꺼낸 지연 작업을 처리할 때 슬롯의 재사용 여부를 다음 두 조건으로만 검사합니다(`ReassemblyDeliveryPipeline.cs:50-51`):
    ```csharp
    var slot = _arena.SlotAt(work.SlotIndex);
    if (slot.State != ReassemblySlotState.Open) continue;      // already reclaimed
    if (slot.ReassemblyId != work.ReassemblyId) continue;      // the slot was reused
    ```
  - 슬롯의 `slot.ConnectionTag != work.ConnectionTag` 검사가 누락되어 있습니다.
  - 만약 연결 A의 완성 메시지가 큐에 적립된 후 폴링(배달) 전에 연결 A가 회수(`ReclaimConnection`)되어 해당 슬롯이 반납되고, 동일한 `ReassemblyId`를 사용하는 연결 B가 해당 슬롯을 할당받아 오픈한 경우, 파이프라인은 슬롯 재사용을 감지하지 못하고 연결 B의 슬롯 데이터를 연결 A의 배달 흐름으로 처리하거나 연결 B의 슬롯 및 버퍼 리스를 조기에 반납(`_arena.Release`, `_pool.Return`)해 버립니다.
- **재현 방법**:
  1. 연결 A(`Tag = 0x01`)에서 `ReassemblyId = 1`인 메시지를 완성시켜 `_deferredWork`에 `(SlotIndex = K, ConnectionTag = 0x01, ReassemblyId = 1)` 작업이 적립되도록 합니다.
  2. 폴링(`DrainToApplication`)이 실행되기 전에 연결 A를 회수(`ReclaimConnection(0x01)`)하여 슬롯 K가 자유 목록으로 반환되게 합니다.
  3. 연결 B(`Tag = 0x02`)에서 `ReassemblyId = 1`인 단일 조각(1조각 완성) 메시지를 전송하여 슬롯 K를 할당받고 즉시 완성되게 합니다.
  4. `DrainToApplication`을 호출합니다.
  5. `DrainToApplication`은 큐의 작업(연결 A 대상)을 꺼내 `slot.ReassemblyId == work.ReassemblyId` (1 == 1)만 확인하고 통과하여, 연결 B의 슬롯 K를 해제하고 버퍼 풀에 반환합니다. 연결 B의 후속 처리는 이미 해제된 버퍼 및 슬롯에 접근하게 됩니다.
- **확신도**: 확신

### 2. FragmentOffsetBoundsFragment.Evaluate 내 오프셋 초과 검사의 도달 불가능성
- **유형**: 죽은 코드
- **어디**:
  - `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:49-58`
- **무엇이 어긋나는가**:
  - `FragmentOffsetBoundsFragment.Evaluate`의 54~57행은 다음과 같이 `offset + expected > total`을 검사하여 초과 시 `FragmentOffsetOutOfBounds`를 반환하도록 되어 있습니다:
    ```csharp
    if (offset + expected > total)
    {
        return Verdict<FragmentPlacementRecord>.Reject(DropReason.FragmentOffsetOutOfBounds, connectionTag, tick);
    }
    ```
  - 그러나 48행에서 계산되는 `expected`는 `header.ExpectedPayloadLengthBytes`에서 가져오며, `FragmentationHeaderRecord`의 구현은 다음과 같습니다:
    ```csharp
    public int ExpectedPayloadLengthBytes
    {
        get
        {
            int uniform = UniformFragmentPayloadBytes;
            int offset = FragmentIndex * uniform;
            int remaining = (int)TotalLengthBytes - offset;
            return remaining < uniform ? remaining : uniform;
        }
    }
    ```
  - 43행의 `if (offset >= total)`을 통과한 상태에서 `remaining = total - offset > 0`이 항상 성립하며, `expected`는 `min(remaining, uniform) <= total - offset`이 수학적으로 보장됩니다.
  - 따라서 `offset + expected <= offset + (total - offset) = total`이 항상 성립하므로 `offset + expected > total` 조건은 어떠한 입력에서도 참이 될 수 없습니다.
- **재현 방법**:
  - `FragmentationHeaderRecord`의 임의의 조합에 대해 43행(`offset < total`)을 만족하고 49행(`arrivedPayloadLengthBytes == expected`)을 만족하는 입력을 주입할 때, `offset + expected > total` 조건문(54행)은 항상 `false`로 평가되어 56행의 반환문은 도달할 수 없습니다.
- **확신도**: 확신
