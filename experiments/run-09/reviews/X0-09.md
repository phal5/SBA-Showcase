## 결점

### 1. `Realtime.Assembly.csproj` 주석과 실제 어셈블리 내용의 직접 모순
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/Realtime.Assembly.csproj:4` 와 `src/Realtime.Assembly/DatagramSecurity/SessionKeys.cs:1` / `src/Realtime.Assembly/DatagramSecurity/DatagramSealer.cs:1`
- **무엇이 어긋나는가**: `Realtime.Assembly.csproj` 3~7행의 주석은 `"D7 메시지 조립만. 소켓·암호·핸드셰이크·채널은 이 어셈블리에 없다."`라고 명시하고 있으나, 보안 확장(`DatagramSecurity`)을 거치면서 AES-256-GCM 암호화/복호화(`DatagramSealer`, `DatagramOpener`) 및 HKDF 키 유도(`SessionKeys`) 등의 암호 계층 구현체가 해당 어셈블리 내에 직접 추가되었다. 프로젝트 파일 주석이 어셈블리의 실제 구성과 정면으로 모순된다.
- **재현 방법**: `src/Realtime.Assembly/Realtime.Assembly.csproj` 4행의 주석과 `src/Realtime.Assembly/DatagramSecurity/` 디렉터리 내 암호화 구현 파일들의 존재를 대조한다.
- **확신도**: 확신

### 2. `MessageSplitter.WriteFragment`의 내부 스크래치 쓰기 실패 시 잘못된 매개변수 이름 예외 발생
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:186-187`
- **무엇이 어긋나는가**: 186행의 `if (!header.TryWrite(frame))`는 분할기 내부 버퍼인 `_frameScratch`(`frame`)에 조각 머리말을 기록할 공간이 부족할 때 실패하는 조건문이다. 그러나 187행에서 예외를 던질 때 `nameof(datagramDestination)`를 인자 이름으로 전달하여, 호출자가 넘긴 목적지 버퍼(`datagramDestination`)가 잘못된 것처럼 오도한다(`datagramDestination`의 크기 검사는 174~175행에서 이미 완료됨).
- **재현 방법**: 코드 검사로 확인 가능. `frame.Length < FragmentHeader.Size`인 상태에서 `header.TryWrite(frame)`가 실패할 경우 던져지는 `ArgumentException.ParamName`이 `"datagramDestination"`으로 반환된다.
- **확신도**: 확신

### 3. `DropReason.cs` 문서 주석의 추가 항목 수 진술 불일치
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/Stubs/DropReason.cs:6-7` 와 `src/Realtime.Assembly/Stubs/DropReason.cs:37-70`
- **무엇이 어긋나는가**: 파일 상단 요약 주석 6~7행에는 `"두 항목(LateFragment, GlobalReassemblyBudgetExceeded)은 구현하며 추가했다"`라고 적혀 있으나, 보안 확장 및 방향별 상한 확장을 거치며 37~70행에 7개 항목(`MalformedDatagram`, `SealOpenFailed`, `ReplayedSequence`, `SequenceOutsideReplayWindow`, `EpochGraceExpired`, `UnknownEpoch`, `InboundDatagramTooLarge`)이 추가되어 총 9개 항목이 추가되었다. 상단 요약 설명이 하단 열거형 내용과 불일치한다.
- **재현 방법**: `src/Realtime.Assembly/Stubs/DropReason.cs`의 6~7행 주석과 37~70행 열거형 정의를 대조한다.
- **확신도**: 확신

### 4. `PathSizeClamp.Clamp`의 `options` null 검사 누락 및 예외 형식 불일치
- **유형**: 미강제 불변식
- **어디**: `src/Realtime.Assembly/Stubs/PathSizeClamp.cs:16-17` 와 `src/Realtime.Assembly/Stubs/PathSizeClamp.cs:22, 29`
- **무엇이 어긋나는가**: 같은 클래스의 `IsWithinRange`(22행) 및 `Require`(29행)는 `ArgumentNullException.ThrowIfNull(options)`를 통해 `options` 인자의 null 불변식을 명시적으로 강제하고 `ArgumentNullException`을 발생시킨다. 반면 `Clamp`(16~17행)는 null 검사 없이 `options.DatagramFloorBytes`에 바로 접근하여, `options`가 null일 때 `ArgumentNullException` 대신 `NullReferenceException`이 발생한다.
- **재현 방법**: `PathSizeClamp.Clamp(null!, 1300)`을 호출하면 `ArgumentNullException`이 아닌 `NullReferenceException`이 발생한다.
- **확신도**: 확신

### 5. `EngineOptions.Validate()` 내 K9 관계 검사의 항진(항상 참) 조건 및 유효 검사 누락
- **유형**: 죽은 코드
- **어디**: `src/Realtime.Assembly/Stubs/EngineOptions.cs:240` 와 `src/Realtime.Assembly/Stubs/EngineOptions.cs:245-246`
- **무엇이 어긋나는가**: 
  - 240행에서 `(long)MaxFragmentsPerMessage * FragmentPayloadFloor >= MaxMessageBytes` (K4)를 검사한다.
  - 245~246행에서 `(long)MaxFragmentsPerMessage * FragmentPayloadCeiling >= MaxMessageBytes`를 K9 검사로 수행한다.
  - 214행에서 `DatagramMaxBytes >= DatagramFloorBytes`를 강제하므로, 정의상 `FragmentPayloadCeiling >= FragmentPayloadFloor`는 항상 참이다.
  - 따라서 240행이 통과하면 245행은 산술적으로 절대 실패할 수 없는 항상 참(tautology)인 죽은 조건문이다.
  - 실제 K9이 의도했던 상한 검사(`FragmentsForDatagram(DatagramMaxBytes) <= MaxFragmentsPerMessage`)는 252행(`RequireRelationsFor`)에서 수행되므로 245행의 검사는 무의미하게 중복된다.
- **재현 방법**: 240행이 통과하는 임의의 `EngineOptions`에 대해 245행의 조건식을 평가하면 항상 `true`가 나온다. 245행이 `false`가 되는 입력은 240행에서 먼저 예외가 발생하므로 245행의 실패 경로는 도달 불가능하다.
- **확신도**: 확신

### 6. `SealedDatagramIntake.Offer`에서 되돌리기 표 거절 시 `reason`이 `DropReason.None`으로 소거되는 문제
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/DatagramSecurity/SealedDatagramIntake.cs:87-89`
- **무엇이 어긋나는가**: `SealedDatagramIntake.Offer` 메서드는 `out DropReason reason`을 반환 매개변수로 노출한다. 87행에서 `reason = DropReason.None;`으로 초기화한 후 88행에서 `_table.Offer`를 호출한다. 만약 `_table.Offer`가 예산 초과(`BudgetExceeded`), 지연 조각(`Late`), 중복(`Duplicate`), 정합성 오류(`Inconsistent`) 등으로 수용을 거절하더라도, `SealedDatagramIntake.Offer`는 해당 거절 `FragmentAdmission`을 반환하면서 `reason`은 여전히 `DropReason.None`으로 반환한다. 이로 인해 호출자가 비-Accept 반환 시 `reason`을 확인하면 원인 사유를 얻을 수 없다.
- **재현 방법**:
  1. 연결의 되돌리기 예산(`B_conn`)을 초과하는 유효하게 봉인된 조각 데이터그램을 생성한다.
  2. `peer.Intake.Offer(datagram, now, out _, out DropReason reason)`을 호출한다.
  3. 반환값은 `FragmentAdmission.BudgetExceeded`이지만, `reason` 출력값은 `DropReason.None`이 된다.
- **확신도**: 확신
