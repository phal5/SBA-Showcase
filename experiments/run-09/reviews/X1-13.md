### 1. `Program.cs` 클래스 문서 주석의 검사 개수 불일치
- **유형**: 자기모순
- **어디**: `harness/Program.cs:22` 와 `harness/Program.cs:42-65`
- **무엇이 어긋나는가**: `harness/Program.cs` 22행의 클래스 요약 주석에는 `"Fifteen checks, each printing PASS or FAIL with numbers; a non-zero exit code if any of them fails."`라고 15개의 검사가 존재한다고 기술되어 있습니다. 그러나 실제 `Program.Main()` 내 `checks` 배열(42~65행)에는 `Check01`부터 `Check21`까지 총 21개의 검사가 등록되어 실행됩니다. 비대칭 경로 상한 확장 단계에서 검사 16~21이 추가되었으나, 하네스 파일 서두의 문서 주석이 갱신되지 않고 방치되었습니다.
- **재현 방법**: `harness/Program.cs` 22행의 주석 수치("Fifteen checks")와 42~65행의 `checks` 배열 원소 개수(21개), 그리고 `dotnet run` 실행 시 콘솔에 출력되는 `"all 21 checks passed"`를 비교하면 주석과 실제 코드가 불일치함을 직접 확인할 수 있습니다.
- **확신도**: 확신

### 2. `DatagramOpenPipeline.OpenDatagram`의 도달 불가능한 헤더 파싱 실패 분기
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72` 와 `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96`
- **무엇이 어긋나는가**: `DatagramOpenPipeline.OpenDatagram`의 1단계 길이 검사(68~72행)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes`(53 B)를 먼저 검사하여 거절합니다. 따라서 2단계 헤더 파싱(93행)에 도달하는 모든 데이터그램은 길이가 최소 53 B 이상입니다. 그런데 2단계에서 호출하는 `SealedDatagramHeaderRecord.TryParse(datagram, out var header)`는 `datagram.Length < WireBytes`(24 B)일 때만 `false`를 반환합니다. 따라서 93행의 `if (!SealedDatagramHeaderRecord.TryParse(datagram, out var header))` 조건은 항상 `false`이며, 95행의 `return Refuse(DropReason.SealedDatagramLengthOutOfRange, connectionTag, tick, 0U);` 분기는 어떤 입력으로도 도달할 수 없는 죽은 코드입니다.
- **재현 방법**:
  1. 24 B 미만의 데이터그램(예: 10 B)을 `DatagramOpenPipeline.OpenDatagram`에 입력하면 1단계(68행)에서 `datagram.Length < 53`에 걸려 line 71에서 즉시 반환되므로 2단계(93행)에 도달하지 못합니다.
  2. 53 B 이상의 데이터그램을 입력하면 `datagram.Length >= 53 > 24`이므로 `TryParse`는 항상 `true`를 반환하여 line 95의 거절 분기에 진입하지 못합니다.
  3. 따라서 line 95는 실행 도달이 불가능합니다.
- **확신도**: 확신

### 3. `MessageSplitPlanRecord`가 진술한 불변식을 스스로 강제하지 않음
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Records/MessageSplitPlanRecord.cs:12-17` 와 `src/Assembly/Records/MessageSplitPlanRecord.cs:24-29`
- **무엇이 어긋나는가**: `MessageSplitPlanRecord`의 문서 주석(12~17행)에서는 설계 원칙(Whitepaper §3.7: "the invariants of a value live in the class that holds the value")을 인용하며 다음 4가지 불변식을 명시하고 있습니다:
  1. `1 ≤ FragmentCount ≤ MaxFragmentsPerMessage`
  2. `FragmentCount == ceil(TotalLengthBytes / UniformFragmentPayloadBytes)` (고정점)
  3. `UniformFragmentPayloadBytes ≤ the path's per-fragment payload`
  4. 모든 조각 경계가 `[0, TotalLengthBytes)` 범위 내에 위치함
  그러나 `MessageSplitPlanRecord`의 `public` 생성자(24~29행)는 전달된 인자에 대해 아무런 유효성 검사나 불변식 강제를 수행하지 않고 값을 그대로 대입하며, `FragmentationHeaderRecord`나 `PathDatagramLimitsRecord`처럼 자체 검증 메서드(`FindDeclaredInvariantViolation`)도 제공하지 않습니다. 불변식이 타입 내에 살아있다고 선언했으나 실제로는 외부 호출자(`MessageSplitFragment`)에 전적으로 의존하며 타입 자체는 불변식을 강제하지 않습니다.
- **재현 방법**: C# 코드에서 `new MessageSplitPlanRecord(totalLengthBytes: -100, fragmentCount: 9999, uniformFragmentPayloadBytes: 0)`와 같이 4가지 불변식을 모두 위반하는 인자를 주어 생성자를 호출하면, 예외나 검증 실패 없이 유효하지 않은 레코드 인스턴스가 그대로 생성됩니다.
- **확신도**: 확신

### 4. `ReassemblyAggregate` 및 `SecurityAggregate` 주석의 보고 필드 개수 불일치
- **유형**: 자기모순
- **어디**: `src/Assembly/Aggregates/ReassemblyAggregate.cs:21` 와 `src/Assembly/Aggregates/ReassemblyAggregate.cs:26-40` (및 `src/Security/Aggregates/SecurityAggregate.cs:16` 와 `src/Security/Aggregates/SecurityAggregate.cs:27-41`)
- **무엇이 어긋나는가**:

2. **`EngineConstantsRecord.FindViolatedConstantRelation`의 CS0162 (도달할 수 없는 코드 경고)**
   - 상수 간의 비교식(`MaxMessageBytes > ReassemblyBytesPerConnection` 등)은 컴파일 타임에 폴딩되어 컴파일러가 실패 분기를 dead branch로 처리합니다. 이는 K1~K9, X1~X8 불변식이 컴파일 타임에 만족됨을 증명하는 동시에 런타임에 상수가 수정될 경우 즉시 검증되도록 의도적으로 배치된 구조이며, `#pragma warning disable CS0162`로 명시적 관리되고 있으므로 결함이 아닙니다.

3. **`DropReason.SealKeyScheduleExhausted` 및 되돌리기 4개 축 거절 사유의 산술적 도달 불가능성**
   - `SealKeyScheduleExhausted`는 관계 X7(`EpochByteLimit` 16 MiB 제약)에 의해 2^64 순번 소진 전에 시대가 넘어가므로 도달 불가능하며, 되돌리기 4개 축(`ReassemblyPerConnectionByteBudgetExhausted` 등) 역시 슬롯 수 예산이 먼저 소진되어 도달 불가능합니다. 이는 설계 및 검증 과정에서 이미 증명되고 Check07 등에서 의도적으로 보존·검증하고 있는 불변식 특성이며, 상수가 조정될 경우 도달 가능해지는 방어적 사유 목록(S2 규칙)이므로 결함이 아닙니다.

4. **`AesGcm.Decrypt` 실패 시의 `CryptographicException` 발생**
   - .NET `AesGcm` API는 태그 불일치 시 예외를 던지도록 설계되어 있으며, `EpochKeyResource.TryOpen`에서 이 예외를 최단 지점에서 잡아 `false`로 변환하여 상위 파이프라인에 예외가 누출되지 않도록 처리하고 있습니다. 정상 경로(steady state)의 무할당(E10) 요건을 위반하지 않으므로 결함이 아닙니다.
