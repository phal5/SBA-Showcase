## 결점

### 1. 지연 배달 큐 처리 시 슬롯의 연결 태그(ConnectionTag) 검증 누락으로 인한 교차 연결 슬롯 오인 및 조기 해제
- **유형**: 미강제 불변식
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50-68`
  - `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:8-24`
  - `DEVIATIONS.md:40`
- **무엇이 어긋나는가**:
  `DEVIATIONS.md` 40행에서 `ReassemblyId`는 전역이 아닌 연결별(connection-scoped) 식별자 `(ConnectionTag, ReassemblyId)`로 명시되어 있습니다. `DeferredReassemblyDeliveryRecord` 역시 `ConnectionTag`와 `ReassemblyId`를 함께 기록합니다.
  그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 큐에서 꺼낸 작업(`work`)을 처리할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag == work.ConnectionTag`를 검사하지 않습니다.
  만약 연결 A의 메시지 조립이 완료되어 배달 큐에 적립된 후, 배달 실행 전에 연결 A가 회수(reclaim)되어 슬롯이 해제되고, 동일한 슬롯 인덱스가 동일한 `ReassemblyId`(예: 1)를 사용하는 연결 B에 재할당된다면, `DrainToApplication`은 슬롯의 연결 태그가 바뀌었음을 감지하지 못하고 연결 B의 조립 데이터를 연결 A의 배달 작업으로 처리한 뒤 연결 B의 슬롯을 조기 반납(`_arena.Release`, `_pool.Return`)해 버립니다.
- **재현 방법**:
  1. `AssemblyWorld` 환경에서 연결 태그 `0xA`로 `ReassemblyId = 1`인 메시지의 모든 조각을 수신하여 완성을 트리거합니다 (`_deferredWork`에 `SlotIndex = 0, ConnectionTag = 0xA, ReassemblyId = 1` 적립).
  2. `Poll`을 호출하여 배달하기 전에, 연결 태그 `0xA`를 회수합니다 (`world.Reclamation.ReclaimConnection(0xA)`). 슬롯 0이 자유 목록으로 반환됩니다.
  3. 연결 태그 `0xB`로 `ReassemblyId = 1`인 메시지의 조각을 전송하여 슬롯 0을 할당받고 완성을 트리거합니다 (`_deferredWork`에 `SlotIndex = 0, ConnectionTag = 0xB, ReassemblyId = 1` 적립).
  4. `world.Delivery.DrainToApplication(world.Sink)`를 호출합니다.
  5. 첫 번째 큐 아이템(연결 `0xA` 대상)이 실행될 때 `slot.ReassemblyId == work.ReassemblyId` (둘 다 1) 조건이 참이 되어 연결 `0xB`의 페이로드를 전달하고 슬롯 0을 즉시 반납/무효화합니다.
  6. 두 번째 큐 아이템(연결 `0xB` 대상)이 실행될 때 슬롯 0은 이미 반납되어 `slot.State != ReassemblySlotState.Open`이 되므로 연결 `0xB`의 배달이 누락됩니다.
- **확신도**: 확신

### 2. 마감 시각 만료 검사(SweepExpired)가 완료되어 배달 대기 중인 슬롯을 미완성 만료로 오판하여 폐기
- **유형**: 자기모순 / 미강제 불변식
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyExpirySweepPipeline.cs:44-60`
  - `src/Assembly/Pipelines/ReassemblyExpirySweepPipeline.cs:9`
  - `harness/Program.cs:1649-1650`
- **무엇이 어긋나는가**:
  `ReassemblyExpirySweepPipeline`의 주석에는 `"what is left unfinished is reclaimed once enough time has passed"`라고 명시되어 있어, 미완성(unfinished) 상태로 남겨진 조립 슬롯만을 만료 회수해야 합니다.
  그러나 `SweepExpired()`는 `_arena.OpenSlots()`를 순회하며 슬롯의 도착 비트맵이 완성(`ReassemblyCompletionFragment.Evaluate(slot.ArrivalBitmap, slot.FragmentCount).IsComplete`)되었는지 여부를 확인하지 않고, 오직 `ReassemblyDeadlineFragment.Evaluate(slot.DeadlineTick, tick) == Reclaim`만으로 회수를 결정합니다.
  `AssemblyWorld.Poll`의 실행 순서상 `Sweep.SweepExpired()`가 `Delivery.DrainToApplication()`보다 먼저 실행되므로, 모든 조각이 도착하여 완성이 적립되었더라도 애플리케이션 `Poll`이 마감 시각(`DeadlineTick`) 이후에 진입하면 완료된 정상 메시지가 `ReassemblyDeadlineExpired`로 폐기되고 버퍼 대여가 회수되어 배달되지 못합니다.
- **재현 방법**:
  1. tick 1,000에서 메시지의 모든 조각을 수신합니다 (`AcceptSealedDatagram`이 `Completed`를 반환하고 슬롯의 비트맵이 모두 채워짐).
  2. 같은 tick에서 `Poll`을 돌리지 않고, 시간을 `tick = 1,000 + EngineConstantsRecord.ReassemblyDeadlineMilliseconds` (21,000)으로 진행한 뒤 `world.Poll(21_000)`을 호출합니다.
  3. `Poll` 내부에서 `Sweep.SweepExpired()`가 먼저 실행되어 슬롯을 만료로 판정하고 `_arena.Release` 및 `_pool.Return`을 수행하며 `DropReason.ReassemblyDeadlineExpired`를 1 증가시킵니다.
  4. 뒤이어 실행되는 `Delivery.DrainToApplication()`은 슬롯이 이미 닫혀 있어 배달을 건너뛰고, `world.Sink.Deliveries.Count`는 0이 됩니다.
- **확신도**: 확신

### 3. `FragmentOffsetBoundsFragment.Evaluate` 내의 도달 불가능한 불필요 조건문
- **유형**: 죽은 코드
- **어디**:
  - `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:49-58`
- **무엇이 어긋나는가**:
  `FragmentOffsetBoundsFragment.cs` 54행에는 `if (offset + expected > total)` 분기가 존재합니다.
  그러나 직전에 호출되는 `header.ExpectedPayloadLengthBytes`는 `remaining = (int)TotalLengthBytes - offset`에 대해 `remaining < uniform ? remaining : uniform`으로 계산되므로, `expected`는 수학적으로 항상 `total - offset` 이하입니다.
  따라서 `offset + expected <= total`이 항상 성립하며, 54행의 조건식 `offset + expected > total`은 어떠한 입력에서도 참이 될 수 없는 도달 불가능한 죽은 코드입니다.
- **재현 방법**:
  - `offset < total`을 만족하고 `arrivedPayloadLengthBytes == expected`인 어떠한 입력 조합을 주어도 `offset + expected`가 `total`을 초과하는 상태를 만들 수 없습니다. 54~57행 분기로 진입하는 테스트 케이스는 존재하지 않습니다.
- **확신도**: 확신

### 4. `DatagramOpenPipeline.OpenDatagram` 내의 도달 불가능한 머리말 파싱 실패 분기
- **유형**: 죽은 코드
- **어디**:
  - `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72`
  - `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96`
  - `src/Security/Records/SealedDatagramHeaderRecord.cs:62-73`
- **무엇이 어긋나는가**:
  `DatagramOpenPipeline.cs` 68행에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes` (53 B) 조건을 검사하여 미달 시 즉시 거절하고 반환합니다.
  이후 93행에서 `if (!SealedDatagramHeaderRecord.TryParse(datagram, out var header))`를 검사합니다.
  `SealedDatagramHeaderRecord.TryParse`는 오직 `source.Length < WireBytes` (24 B)일 때만 `false`를 반환합니다.
  앞선 68행의 검사를 통과한 데이터그램은 길이가 항상 53 B 이상이므로 `TryParse`는 항상 `true`를 반환하며, 93~96행의 실패 거절 분기는 결코 실행될 수 없습니다.
- **재현 방법**:
  - 68행 길이 검사를 통과한 임의의 바이트 배열에 대해 `TryParse`가 `false`를 반환하는 경우는 존재하지 않으므로 93~96행 분기로 진입할 수 없습니다.
- **확신도**: 확신

### 5. `FragmentationHeaderRecord.UniformFragmentPayloadBytes` 주석의 반환 타입 기술 오류
- **유형**: 자기모순
- **어디**:
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:42`
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:64-86`
- **무엇이 어긋나는가**:
  `FragmentationHeaderRecord.cs` 42행 주석에는 `Meaningless unless <see cref="FindDeclaredInvariantViolation"/> returned null.`이라고 적혀 있습니다.
  그러나 `FindDeclaredInvariantViolation()` 메서드의 실제 반환 타입은 열거형 `DropReason`이며, 불변식이 만족될 때 반환하는 값은 `DropReason.None`(값 0)이지 `null`이 아닙니다. 참조 타입/널 가능 타입이 아니므로 `null`을 반환할 수 없습니다.
- **재현 방법**:
  - 소스 코드 42행의 문서 주석과 64행 메서드 시그니처(`public DropReason FindDeclaredInvariantViolation()`)를 대조하여 확인 가능합니다.
- **확신도**: 확신
