## 결점이 아니라고 판단한 것

1. **`DatagramOpener.TryOpen`에서 다음 시대로 전환(`promoting == true`) 시 `Promote` 호출과 `state.Window.Accept`의 상태 갱신**
   - **위치**: `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:150-154`, `190-194`, `203-210`
   - **검토 내용**: `state`는 클래스 `EpochState`의 참조이며 `header.Epoch == _next.Epoch`일 때 `state = _next`로 할당된다. `Promote(now)` 호출 시 `_current = _next`로 참조가 넘어가고 `_next`는 새로 생성되지만, 로컬 변수 `state`가 가리키는 `EpochState` 인스턴스는 여전히 승격된 새 `_current` 인스턴스다. 따라서 이어서 호출되는 `state.Window.Accept(header.Sequence)`는 승격된 현재 시대의 `ReplayWindow`에 정확히 반영된다. 구조체 복사나 참조 불일치 버그가 없음을 확인했다.

2. **`MessageSplitter._frameScratch`의 크기 할당 및 여러 연결 간 공유**
   - **위치**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:88-89`, `168-171`
   - **검토 내용**: 스크래치 버퍼는 `FragmentHeader.Size + _options.FragmentPayloadCeiling` 크기로 할당된다. 각 연결의 `plan.FragmentPayload`는 `limits.OutboundFragmentPayload <= FragmentPayloadCeiling`이므로, 어떤 연결의 어떤 조각 프레임도 이 스크래치 크기를 초과하지 않는다. 또한 단일 스레드 엔진 폴 루프 전제 하에서 봉인 직후 `CryptographicOperations.ZeroMemory(frame)`로 즉시 소거되므로 연결 간 데이터 유출이나 버퍼 오버플로가 발생하지 않는다.

3. **`ReassemblyTable._recentlyCompleted`의 초기화 및 `MessageId = 0` 처리**
   - **위치**: `src/Realtime.Assembly/MessageAssembly/ReassemblyTable.cs:47-48`, `245-258`
   - **검토 내용**: 최근 완성된 메시지 ID 링 버퍼는 `long[]` 타입으로 선언되고 `-1L`로 채워진다. `messageId`는 `uint`이므로 0을 포함한 모든 유효 메시지 ID는 `0L` 이상의 양수로 변환되어 저장/비교된다. 초기 빈 슬롯(`-1L`)과 `messageId = 0`이 혼동되지 않는다.

4. **`ReassemblyBudget` 값 타입과 `ReassemblyBudget.Shared` 참조 타입의 분리**
   - **위치**: `src/Realtime.Assembly/MessageAssembly/ReassemblyBudget.cs:16-54`, `ReassemblyTable.cs:29`, `52`
   - **검토 내용**: 계획 §2 D7 명세에 따라 `ReassemblyBudget`을 `struct`로 유지하면서, 여러 연결이 공유해야 하는 전역 축은 내부 클래스 `ReassemblyBudget.Shared` 참조로 전달하도록 설계되었다. `ReassemblyTable` 내부에서는 필드 `_budget`을 직접 수정하며, `Budget` 프로퍼티를 통해 외부로 나갈 때는 읽기 전용 스냅숏으로 안전하게 복사된다.

5. **`SealedDatagramIntake.Offer`에서 복호화 실패 시와 D7 표 수용 시의 `DropReason` 반환 처리**
   - **위치**: `src/Realtime.Assembly/DatagramSecurity/SealedDatagramIntake.cs:65-89`
   - **검토 내용**: `SealedDatagramIntake.Offer`의 `out DropReason reason`은 봉인 계층에서 거절되었을 때의 사유(`SealRejected`, `MalformedFrame` 등)를 반환하는 용도이다. 데이터그램이 성공적으로 개봉되어 `_table.Offer`로 전달된 이후의 거절(`Inconsistent`, `Duplicate`, `BudgetExceeded`, `Late`)은 `_table.Offer` 내부에서 해당 사유를 `_counters`에 집계하고 `FragmentAdmission` 결과를 반환하는 책임 분리가 문서(DEVIATIONS.md 이탈 #5) 및 주석과 완전히 일치한다.

6. **도착 비트맵 64비트(`ulong`)와 조각 수 상한 `F = 64`의 경계 정합성**
   - **위치**: `src/Realtime.Assembly/MessageAssembly/ReassemblyContext.cs:44`, `63-67`, `108`
   - **검토 내용**: `_arrivalBitmap`은 `ulong` 1개(64비트)로 관리된다. `TotalFragments` 상한은 `MaxFragmentsPerMessage = 64`로 강제되며, `1UL << index` 연산에서 `index`가 0부터 63까지 정확히 대응한다. 또한 실제 경로 하한(`D_floor = 1200`, `H = 58`, `P_floor = 1142`)에서 `M = 65536` 메시지가 분할될 때 도달 가능한 최대 조각 수는 58조각이므로 64비트 범위를 결코 초과하지 않는다.
