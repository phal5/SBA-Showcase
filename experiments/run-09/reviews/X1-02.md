## 결점

### 1. `ReassemblyDeliveryPipeline`의 연결 태그 검증 누락으로 인한 타 연결 슬롯 오배달 및 활성 슬롯/버퍼 조기 반납 (Use-After-Free)
- **유형**: 미강제 불변식 / 자원 누수
- **어디**: 
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50-52`
  - `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:11-23`
- **무엇이 어긋나는가**: 
  `DEVIATIONS.md` #2 및 §"계획이 답을 주지 못한 지점"에서 `ReassemblyId`는 연결별(per-connection)로 격리된 식별자이며 색인 키는 `(연결 태그, ReassemblyId)`의 쌍이라고 명시하고 있습니다. 이에 맞춰 `ReassemblyCompletionTrigger`가 발행하는 지연 작업 레코드 `DeferredReassemblyDeliveryRecord`에도 `ConnectionTag`가 필드로 포함되어 있습니다.
  그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 지연 큐에서 작업을 꺼내 슬롯의 유효성을 검사할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag != work.ConnectionTag`를 검사하지 않습니다.
  이로 인해 연결 A의 메시지 조립이 완료되어 지연 배달 큐에 적립된 후, 실제 배달(`DrainToApplication`)이 수행되기 전에 연결 A가 회수(`ReclaimConnection`)되어 해당 슬롯이 반납되고, 동일한 슬롯에 다른 연결 B가 우연히 같은 `ReassemblyId`를 사용하여 슬롯을 열었을 경우, 연결 B의 슬롯을 연결 A의 작업으로 오인하여 배달을 시도하고 `_arena.Release(slot)` 및 `_pool.Return(lease)`를 호출하여 활성 상태인 연결 B의 슬롯과 버퍼 풀 리스를 즉시 파괴(use-after-free 및 조기 반환)합니다.
- **재현 방법**:
  1. 연결 A(`0xA1`)를 생성하고 `ReassemblyId = 1`인 메시지의 모든 조각을 수신하여 `ReassemblyCompletionTrigger.FileDelivery`가 `DeferredReassemblyDeliveryRecord(SlotIndex=0, ConnectionTag=0xA1, ReassemblyId=1, ...)`를 `_deferredWork` 큐에 인큐하도록 합니다.
  2. `world.Poll` 또는 `Delivery.DrainToApplication`을 호출하기 전에 `world.Reclamation.ReclaimConnection(0xA1)`을 호출하여 연결 A를 회수합니다 (슬롯 0이 해제되어 `_freeSlotIndices`에 반환됨).
  3. 새로운 연결 B(`0xB2`)를 생성하고 `ReassemblyId = 1`인 메시지의 조각을 수신합니다. 슬롯 0이 연결 B에 할당되어 `Open` 상태가 됩니다.
  4. `Delivery.DrainToApplication(sink)`를 호출합니다.
  5. `ReassemblyDeliveryPipeline`은 `slot.ConnectionTag`를 확인하지 않으므로 `slot.ReassemblyId == 1`만 보고 연결 B의 슬롯 0을 처리 대상으로 삼아 `_arena.Release(slot)` 및 `_pool.Return(lease)`를 호출합니다. 연결 B의 활성 슬롯과 버퍼 풀 리스가 연결 B의 조립 완료 전에 조기 해제되어 파괴됩니다.
- **확신도**: 확신

### 2. `FragmentationHeaderRecord.UniformFragmentPayloadBytes` 주석과 `FindDeclaredInvariantViolation` 반환형 불일치
- **유형**: 자기모순
- **어디**: 
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:42`
  - `src/Assembly/Records/FragmentationHeaderRecord.cs:64`
- **무엇이 어긋나는가**: 
  `FragmentationHeaderRecord.cs` 42행의 `UniformFragmentPayloadBytes` 속성 XML 문서 주석에는 `"Meaningless unless <see cref="FindDeclaredInvariantViolation"/> returned null."`이라고 명시되어 있습니다.
  그러나 64행의 `FindDeclaredInvariantViolation()` 메서드 정의는 반환형이 `DropReason`(열거형 struct)이며, 불변식이 모두 만족될 때 `DropReason.None`을 반환합니다. `DropReason`은 값 형식이므로 결코 `null`을 반환할 수 없으며, 주석의 기술이 실제 코드 시그니처 및 반환값과 모순됩니다.
- **재현 방법**: 
  `src/Assembly/Records/FragmentationHeaderRecord.cs`의 42행과 64행을 대조. `FindDeclaredInvariantViolation()`의 반환형은 `DropReason` enum이므로 `header.FindDeclaredInvariantViolation() == null` 비교식은 컴파일되지 않음.
- **확신도**: 확신

### 3. `ReassemblyAggregate` 및 `SecurityAggregate` 문서 주석의 필드 개수와 `EntryRecord` 구조체 정의 불일치
- **유형**: 자기모순
- **어디**: 
  - `src/Assembly/Aggregates/ReassemblyAggregate.cs:21` (vs `src/Assembly/Aggregates/ReassemblyAggregate.cs:28-39`)
  - `src/Security/Aggregates/SecurityAggregate.cs:16` (vs `src/Security/Aggregates/SecurityAggregate.cs:27-40`)
- **무엇이 어긋나는가**: 
  - `ReassemblyAggregate.cs` 21행 주석에는 `"So the report is narrowed to three values — (tick, branch code, connection tag) — written into a fixed-size ring."`라고 적혀 있으나, 28~39행의 실제 `EntryRecord` 구조체는 `Tick`, `Branch`, `ConnectionTag`, `ReassemblyId` 총 4개의 필드를 가집니다.
  - `SecurityAggregate.cs` 16행 주석에는 `"a fixed-size ring of three-value reports"`라고 적혀 있으나, 27~40행의 실제 `EntryRecord` 구조체는 `Tick`, `Branch`, `ConnectionTag`, `Epoch` 총 4개의 필드를 가집니다.
  두 클래스 모두 주석에는 3개 값(three values)으로 축소했다고 기술되어 있으나 실제 코드는 4개 값을 기록하고 있습니다.
- **재현 방법**: 
  `src/Assembly/Aggregates/ReassemblyAggregate.cs` 21행과 28~39행, `src/Security/Aggregates/SecurityAggregate.cs` 16행과 27~40행을 각각 대조.
- **확신도**: 확신
