## 결점

### 1. `DropReason.MalformedDatagram`의 주석 설명과 실제 거절 사유 분리 구현의 모순
- **유형**: 자기모순 / 중복 불일치
- **어디**:
  - `src/Realtime.Assembly/Stubs/DropReason.cs:39`
  - `src/Realtime.Assembly/Stubs/DropReason.cs:64-70`
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:121-125`
  - `ASYMMETRY-NOTES.md:28, 68`
- **무엇이 어긋나는가**:
  - `DropReason.cs:39`의 주석은 `MalformedDatagram`을 `봉인된 데이터그램의 바이트 배치가 어긋난다(너무 짧거나 경로 상한을 넘는다)`라고 설명하고 있습니다.
  - 그러나 방향별 경로 상한(D5)이 도입되면서 "경로 상한을 넘는 데이터그램"은 `DropReason.InboundDatagramTooLarge` (값 15)로 완전히 분리되었고, `DatagramOpener.TryOpen`에서도 `datagram.Length > _limits.Inbound`일 때 `DropReason.InboundDatagramTooLarge`를 반환합니다.
  - `ASYMMETRY-NOTES.md` 28행 및 68행에서도 `MalformedDatagram`과 `InboundDatagramTooLarge`를 분리했다고 명시하고 있으나, `DropReason.cs:39`의 요약 주석에는 여전히 옛 설명인 `(너무 짧거나 경로 상한을 넘는다)`가 그대로 남아 있어 파일 내부 및 구현과 모순됩니다.
- **재현 방법**:
  1. `PathLimits`의 들어오는 쪽 상한이 1,200 B인 상태에서 1,201 B 크기의 데이터그램을 `DatagramOpener.TryOpen`에 전달합니다.
  2. 반환되는 `reason`을 확인하면 `DropReason.InboundDatagramTooLarge`가 나오며, `DropReason.MalformedDatagram`은 경로 상한 초과 시 결코 산출되지 않습니다.
- **확신도**: 확신

### 2. `EngineOptions.Validate()`의 K9 검사 조건이 수학적으로 항상 참(죽은 검사)임
- **유형**: 죽은 코드 / 항상 참인 조건
- **어디**: `src/Realtime.Assembly/Stubs/EngineOptions.cs:240-246`
- **무엇이 어긋나는가**:
  - `EngineOptions.Validate()`에서 214행 `Require(DatagramMaxBytes >= DatagramFloorBytes, ...)`를 통해 `DatagramMaxBytes >= DatagramFloorBytes` (따라서 `FragmentPayloadCeiling >= FragmentPayloadFloor`)가 보장됩니다.
  - 240행에서 K4 검사 `(long)MaxFragmentsPerMessage * FragmentPayloadFloor >= MaxMessageBytes`가 통과하면, `FragmentPayloadCeiling >= FragmentPayloadFloor`이므로 245행의 K9 검사 `(long)MaxFragmentsPerMessage * FragmentPayloadCeiling >= MaxMessageBytes`는 언제나 참이 되어 거짓으로 평가되어 예외를 던지는 경로에 도달할 수 없습니다.
  - D_max에서의 유효성 검증은 실제로 252행의 `RequireRelationsFor(DatagramMaxBytes, ...)`를 통해 이루어지므로, 245행의 K9 `Require` 식은 의미 없는 중복 검사이자 항상 참인 죽은 조건문입니다.
- **재현 방법**:
  - `EngineOptions.Validate()`를 통과하는 임의의 유효한 설정에서 245행의 검사 조건을 단독으로 실패하게 만드는 `EngineOptions` 속성 조합(즉, 214행과 240행을 만족하면서 245행만 실패하는 조합)을 구성할 수 없습니다. (`FragmentPayloadCeiling >= FragmentPayloadFloor`이므로 수학적으로 불가능)
- **확신도**: 확신

### 3. `DatagramOpener.TryOpen` 내 `SealedDatagramHeader.TryRead` 실패 분기 도달 불가능
- **유형**: 도달 불가능한 갈래 / 죽은 코드
- **어디**:
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:111-128`
  - `src/Realtime.Assembly/DatagramSecurity/SealedDatagramHeader.cs:80-84`
- **무엇이 어긋나는가**:
  - `DatagramOpener.TryOpen`의 111행에서 `if (datagram.Length <= DatagramSeal.Overhead)` (40 B)를 검사하여 작거나 같으면 `MalformedDatagram`으로 즉시 반환합니다.
  - 따라서 127행에 도달했을 때 `datagram.Length`는 최소 41 B 이상입니다.
  - 그런데 127행에서 호출하는 `SealedDatagramHeader.TryRead(datagram, ...)`가 실패(`false`)를 반환하는 유일한 조건은 `datagram.Length < Size` (24 B)입니다 (`SealedDatagramHeader.cs:80-84`).
  - `datagram.Length >= 41`이므로 `SealedDatagramHeader.TryRead`는 항상 `true`를 반환하며, 128행의 `return false;` 갈래는 절대 실행될 수 없는 도달 불가능한 코드입니다.
- **재현 방법**:
  - `DatagramOpener.TryOpen`에 어떤 크기와 내용의 바이트 배열을 전달하더라도, 111행의 길이 검사를 통과한 뒤 128행(`SealedDatagramHeader.TryRead` 실패로 인한 `return false`)에 도달하게 만들 수 없습니다.
- **확신도**: 확신

### 4. `MessageSplitter.WriteFragment`의 머리말 쓰기 실패 분기 도달 불가 및 예외 매개변수명 불일치
- **유형**: 도달 불가능한 갈래 / 죽은 코드
- **어디**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:186-187`
- **무엇이 어긋나는가**:
  - `MessageSplitter.WriteFragment`는 185행에서 `frame = _frameScratch.AsSpan(0, frameLength)`로 스팬을 잡습니다. 여기서 `frameLength = FragmentHeader.Size(18) + payloadLength >= 18`입니다.
  - 186행의 `header.TryWrite(frame)`는 대상 스팬 길이가 18 미만일 때만 `false`를 반환하므로, `header.TryWrite(frame)`는 항상 `true`입니다.
  - 만약 이 분기가 실패한다고 가정하더라도, 187행에서 던지는 예외는 `throw new ArgumentException("머리말을 쓸 공간이 없다.", nameof(datagramDestination));`로, 검사 대상인 내부 스크래치 버퍼 `frame`이 아니라 호출자가 전달한 `datagramDestination`을 오류 매개변수명으로 잘못 가리키고 있습니다 (`datagramDestination` 용량 검사는 이미 174행에서 완료됨).
- **재현 방법**:
  - 유효한 `FragmentPlan`과 메시지를 가지고 `WriteFragment`를 호출할 때 187행의 예외가 발생하는 입력을 만들 수 없습니다.
- **확신도**: 의심 (방어적 코드 작성 의도로 볼 수 있으나, 잘못된 매개변수명 지정과 함께 도달 불가능한 분기임)

## 결점이 아니라고 판단한 것

3. **`PathLimits`의 가변 필드 스레드 비안전성 및 D4 계획 세대 관리 미비**:
