## 결점

### 1. `ReassemblyDeliveryPipeline`에서 슬롯 재사용 검증 시 `ConnectionTag` 비교 누락으로 인한 타 연결 슬롯 오염
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:51` 및 `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:8-24`, `DEVIATIONS.md:40-42`
- **무엇이 어긋나는가**:
  `DEVIATIONS.md`(40-42행)와 `ReassemblyArenaResource`는 슬롯 식별 키를 `(ConnectionTag, ReassemblyId)`의 복합 키로 정의하고 있으며, 완료 트리거가 적립하는 `DeferredReassemblyDeliveryRecord`에도 `ConnectionTag`를 필드로 보존하고 있습니다.
  그러나 `ReassemblyDeliveryPipeline.DrainToApplication`의 51행에서는 큐의 작업 항목과 아레나의 슬롯 일치 여부를 검사할 때 `if (slot.ReassemblyId != work.ReassemblyId) continue;`만 검사하고 `slot.ConnectionTag != work.ConnectionTag` 검사를 누락했습니다.
  만약 A 연결의 메시지 조립이 완료되어 큐에 들어간 뒤 배달 전에 A 연결이 회수되고, B 연결이 동일한 `ReassemblyId`로 동일 슬롯 인덱스를 할당받아 열게 되면, `DrainToApplication`은 B 연결의 슬롯을 A 연결의 완료 작업으로 오인하여 배달을 시도하고 슬롯을 해제(`_arena.Release`, `_pool.Return`)하여 B 연결의 정상적인 조립 슬롯을 파괴합니다.
- **재현 방법**:
  1. ConnectionTag `0x1000`으로 메시지 조립을 완료시킨다 (`ReassemblyCompletionTrigger.FileDelivery` 호출로 큐에 `SlotIndex: 0, ConnectionTag: 0x1000, ReassemblyId: 1` 적립).
  2. `Poll`의 `DrainToApplication`이 실행되기 전에 `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0x1000)`을 호출하여 0번 슬롯을 회수한다.
  3. 다른 ConnectionTag `0x2000`이 동일한 `ReassemblyId: 1`로 새 조립을 시작하여 방금 비어 있는 0번 슬롯을 새로 할당받는다 (`slot.ConnectionTag == 0x2000`, `slot.ReassemblyId == 1`, `slot.State == Open`).
  4. `Delivery.DrainToApplication(sink)`를 호출한다.
  5. `ReassemblyDeliveryPipeline`은 `slot.ReassemblyId == work.ReassemblyId`만 검사하므로 `slot.ConnectionTag`가 `0x2000`임에도 검증을 통과하여 0번 슬롯의 버퍼를 해제 및 반납해 버리고, `0x2000` 연결의 조립 상태가 파괴된다.
- **확신도**: 확신

### 2. `FragmentOffsetBoundsFragment` 내의 `offset + expected > total` 도달 불가능한 조건문 (죽은 코드)
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  `FragmentOffsetBoundsFragment.Evaluate` 메서드에서 43행의 `if (offset >= total) return Reject(...)`를 통과하면 항상 `offset < total`이 성립합니다.
  이후 48행의 `int expected = header.ExpectedPayloadLengthBytes;`는 `FragmentationHeaderRecord`의 정의상 `min(total - offset, uniform)`을 반환하므로 언제나 `expected <= total - offset`입니다.
  따라서 `offset + expected <= total`이 수학적으로 항상 참이 되므로, 54행의 `if (offset + expected > total)` 조건은 절대 참이 될 수 없으며 내부의 `Reject(DropReason.FragmentOffsetOutOfBounds)` 블록은 도달 불가능한 죽은 코드입니다.
- **재현 방법**:
  `Evaluate` 함수에 어떤 `FragmentationHeaderRecord`와 페이로드 길이를 입력하더라도, 43행(`offset >= total`) 또는 49행(`arrivedPayloadLengthBytes != expected`)에서 먼저 처리되거나 54행 조건이 `false`가 되어 54행의 거절 분기에는 절대 도달할 수 없습니다.
- **확신도**: 확신

### 3. `DatagramOpenPipeline` 내의 `TryParse` 실패 검사 도달 불가능 (죽은 코드)
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96` 및 `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72`
- **무엇이 어긋나는가**:
  `DatagramOpenPipeline.OpenDatagram`의 1단계(68행)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes (53)`인 경우 이미 거절됩니다.
  2단계(93행)의 `SealedDatagramHeaderRecord.TryParse`는 입력 길이가 `WireBytes (24)` 미만일 때만 `false`를 반환하도록 구현되어 있습니다.
  1단계를 통과한 데이터그램은 길이가 최소 53바이트 이상이므로 `TryParse`는 항상 `true`를 반환하며, 93행의 `if (!SealedDatagramHeaderRecord.TryParse(...))` 분기는 결코 실행될 수 없습니다.
- **재현 방법**:
  `OpenDatagram`에 임의의 길이의 바이트 배열을 전달할 때, 53바이트 미만이면 68행에서 먼저 거절되고, 53바이트 이상이면 `TryParse`가 항상 `true`를 반환하므로 93-96행의 `Refuse` 코드는 실행되지 않습니다.
- **확신도**: 확신
