### 1. `DropReason.LateFragment` 및 `FragmentAdmission.Late` 주석과 실제 만료 메시지 재도착 처리(코드 및 DEVIATIONS.md) 사이의 자기모순
- **유형**: 자기모순
- **어디**:
  - `src/Realtime.Assembly/Stubs/DropReason.cs:31`
  - `src/Realtime.Assembly/MessageAssembly/FragmentAdmission.cs:23`
  - `src/Realtime.Assembly/MessageAssembly/ReassemblyTable.cs:97-101`, `166-167`, `183-186`
  - `DEVIATIONS.md:53-58`
- **무엇이 어긋나는가**:
  `DropReason.cs:31`의 `DropReason.LateFragment` 주석은 `"이미 완성되었거나 회수된 메시지의 조각이 뒤늦게 왔다"`라고 기술하고 있으며, `FragmentAdmission.cs:23`의 `FragmentAdmission.Late` 주석 또한 `"이미 완성되었거나 마감으로 회수된 메시지의 조각이다"`라고 명시하고 있습니다.
  그러나 `ReassemblyTable.cs`의 `ReclaimExpired`(183~186행)는 만료 회수 시 `_recentlyCompleted` 링 버퍼에 메시지 ID를 기록하지 않으며, 오직 정상 완성되어 `Retire`(166~167행)된 메시지 ID만 링 버퍼에 기록됩니다. 따라서 `Offer`(97~101행)는 완성된 메시지에 대해서만 `Late` / `LateFragment`를 산출합니다.
  `DEVIATIONS.md` §(3)에서도 만료된 ID를 링에 넣지 않고 다시 열릴 수 있도록 허용한다고 명시하고 있으므로, 두 열거형 주석에 적힌 "회수된 / 마감으로 회수된 메시지" 설명은 실제 코드 동작 및 설계 결정 문서와 정면으로 모순됩니다.
- **재현 방법**:
  1. 메시지 ID 41인 메시지의 첫 번째 조각을 `ReassemblyTable.Offer`에 투입하여 되돌리기 건을 엽니다.
  2. 단조 시계를 `ReassemblyDeadlineMs`(12,000 ms) 이상 전진시킨 후 `ReassemblyTable.ReclaimExpired`를 호출하여 해당 건을 만료 회수합니다.
  3. 이후 동일한 메시지 ID 41의 유효한 조각을 다시 `ReassemblyTable.Offer`에 투입합니다.
  4. 주석 설명에 따르면 `FragmentAdmission.Late` / `DropReason.LateFragment`로 거절되어야 하지만, 실제로는 새 컨텍스트가 열리며 `FragmentAdmission.Accept`가 반환됩니다.
- **확신도**: 확신

### 2. `DatagramOpener.TryOpen` 내 `SealedDatagramHeader.TryRead` 실패 검사 분기 (도달 불가능한 죽은 코드)
- **유형**: 죽은 코드
- **어디**:
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:111-128`
  - `src/Realtime.Assembly/DatagramSecurity/SealedDatagramHeader.cs:80-84`
- **무엇이 어긋나는가**:
  `DatagramOpener.TryOpen` 111행에서 `datagram.Length <= DatagramSeal.Overhead`(40 B)를 먼저 검사하여 참이면 `MalformedDatagram` 사유로 즉시 반환합니다. 따라서 127행에 도달하는 모든 `datagram`의 길이는 최소 41 B 이상임이 보장됩니다.
  `SealedDatagramHeader.TryRead`가 `false`를 반환하는 유일한 조건은 `datagram.Length < Size`(24 B)뿐이므로, 127행의 `if (!SealedDatagramHeader.TryRead(...))` 검사는 항상 `false`가 되며 128행의 `return false;` 분기는 절대 실행될 수 없는 도달 불가능한 죽은 코드입니다.
- **재현 방법**:
  `DatagramOpener.TryOpen`에 임의의 바이트 배열을 전달할 때, 길이가 40 B 이하이면 111행에서 반환되고, 길이가 41 B 이상이면 `SealedDatagramHeader.TryRead`가 항상 `true`를 반환하므로 128행(`return false;`)에 진입하는 입력을 만드는 것은 불가능합니다.
- **확신도**: 확신

### 3. `MessageSplitter.WriteFragment` 예외 발생 시 잘못된 인자 이름 전달
- **유형**: 자기모순
- **어디**:
  - `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:186-187`
- **무엇이 어긋나는가**:
  `MessageSplitter.WriteFragment` 186행에서 내부 스크래치 버퍼 `frame`에 조각 머리말을 직렬화하는 `header.TryWrite(frame)`의 실패를 검사할 때, 던지는 `ArgumentException`의 매개변수 이름으로 `nameof(datagramDestination)`을 전달하고 있습니다.
  호출자가 제공한 목적지 버퍼 `datagramDestination`의 크기 부족은 174행에서 이미 검사되고 있으며, 187행의 실패는 내부 프레임 버퍼(`_frameScratch`) 또는 계획(`plan`)과 관련된 것이므로 예외에 잘못된 매개변수 이름이 보고됩니다.
- **재현 방법**:
  `header.TryWrite(frame)`이 실패하는 상황이 발생할 경우(예: 프레임 버퍼 슬라이스 길이가 `FragmentHeader.Size` 미만인 경우), 발생한 `ArgumentException.ParamName`이 실제 원인인 내부 프레임 버퍼가 아닌 `"datagramDestination"`으로 잘못 표시됩니다.
- **확신도**: 확신
