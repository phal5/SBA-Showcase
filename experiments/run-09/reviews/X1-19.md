## 결점

### 1. `ReassemblyDeliveryPipeline`에서 슬롯 재사용 여부 검증 시 `ConnectionTag` 누락으로 인한 타 연결 슬롯 오배달 및 조기 파괴
- **유형**: 미강제 불변식
- **어디**:
  - `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:51`
  - `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:11` 및 `DEVIATIONS.md:40`
- **무엇이 어긋나는가**:
  `DEVIATIONS.md`(40행)에서는 `ReassemblyId`가 전역이 아닌 연결별 식별자이며 색인 키가 `(ConnectionTag, ReassemblyId)` 쌍이라고 명시하고 있고, `ReassemblyCompletionTrigger`가 발행하는 지연 배달 레코드(`DeferredReassemblyDeliveryRecord`)에도 `ConnectionTag`가 필드로 포함되어 있습니다.
  그러나 지연 큐에서 항목을 꺼내 배달하는 `ReassemblyDeliveryPipeline.DrainToApplication`에서는 슬롯이 회수/재사용되었는지 확인할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag != work.ConnectionTag`를 검사하지 않습니다.
  만약 한 연결의 재조립이 완료되어 지연 작업이 큐에 들어간 뒤 `DrainToApplication`이 돌기 전에 해당 연결이 회수(Reclaim)되고, 다른 연결이 동일한 슬롯 인덱스에 우연히 같은 `ReassemblyId`로 슬롯을 할당받으면, 이전 연결의 작업 항목이 새 연결의 슬롯을 자기 슬롯으로 착각하여 새 연결의 데이터를 오배달하고 `_arena.Release(slot)` 및 `_pool.Return(lease)`를 호출하여 새 연결의 활성 슬롯과 버퍼를 조기에 파괴합니다.
- **재현 방법**:
  1. 연결 태그 `0x100`으로 1개 조각짜리 메시지(`reassemblyId = 1`)를 수신하여 완료시킵니다. 트리거가 `DeferredReassemblyDeliveryRecord(SlotIndex = 0, ConnectionTag = 0x100, ReassemblyId = 1, ...)`를 큐에 넣습니다. (이때 `Poll`이나 `DrainToApplication`은 호출하지 않습니다.)
  2. `world.Reclamation.ReclaimConnection(0x100)`을 호출하여 연결 `0x100`을 회수합니다. 슬롯 0이 비워지고 자유 슬롯 목록으로 돌아갑니다.
  3. 연결 태그 `0x200`으로 1개 조각짜리 메시지(`reassemblyId = 1`)를 수신합니다. 슬롯 0이 연결 `0x200`에 할당되어 완료 상태가 됩니다.
  4. 이제 `world.Delivery.DrainToApplication(sink)`를 호출합니다.
  5. **결과**: `slot.ConnectionTag`(0x200)와 `work.ConnectionTag`(0x100)의 불일치가 검사되지 않아, `0x100`의 작업 처리에 의해 `0x200`의 슬롯 0이 배달 및 `Release`되어 연결 `0x200`의 슬롯이 파괴됩니다.
- **확신도**: 확신

### 2. `FragmentOffsetBoundsFragment`의 항상 거짓인 불필요한 경계 검사 조건문 (도달 불가능한 죽은 코드)
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  43행의 `if (offset >= total)` 검사를 통과한 시점에서 `offset < total`임이 확정됩니다.
  이후 48행에서 `expected`를 `header.ExpectedPayloadLengthBytes`로부터 구하는데, `ExpectedPayloadLengthBytes`는 `remaining = total - offset; return remaining < uniform ? remaining : uniform;`으로 구현되어 있으므로 항상 `expected <= total - offset` (즉, `offset + expected <= total`)을 만족합니다.
  따라서 54행의 `if (offset + expected > total)` 조건은 수학적으로 절대 `true`가 될 수 없으며, 56행의 `return Verdict<FragmentPlacementRecord>.Reject(...)` 분기는 영원히 도달할 수 없는 죽은 코드입니다.
- **재현 방법**:
  재현할 수 없습니다 (도달 불가능).
  `offset < total`이고 `arrivedPayloadLengthBytes == expected`인 어떤 합법/불법 헤더 입력 조합을 주어도 `ExpectedPayloadLengthBytes`의 산술적 정의로 인해 `offset + expected > total`은 항상 거짓입니다.
- **확신도**: 확신
