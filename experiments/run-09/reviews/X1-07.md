### 1. `ReassemblyDeliveryPipeline` 지연 배달 처리 시 슬롯 재사용 검사에서 `ConnectionTag` 미확인으로 인한 타 연결 슬롯 오배달 및 조기 반환 위험
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50-52` (대조: `DEVIATIONS.md:40`, `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:8-24`, `src/Assembly/Pipelines/ConnectionReassemblyReclamationPipeline.cs:37-58`)
- **무엇이 어긋나는가**: 
  - `DEVIATIONS.md` §27-43에서는 `ReassemblyId`가 연결별(per-connection)로 스코프되며 재조립 상태의 고유 식별자는 `(ConnectionTag, ReassemblyId)` 쌍이라고 명시하고 있습니다. `ReassemblyCompletionTrigger`가 발행하는 `DeferredReassemblyDeliveryRecord` 역시 이를 위해 `ConnectionTag` 필드를 보존합니다.
  - 그러나 `ReassemblyDeliveryPipeline.DrainToApplication`의 슬롯 재사용 검사 루프(50-52행)는 다음과 같이 `ReassemblyId`만 검사하고 `ConnectionTag`의 일치 여부를 검사하지 않습니다:
    ```csharp
    var slot = _arena.SlotAt(work.SlotIndex);
    if (slot.State != ReassemblySlotState.Open) continue;      // already reclaimed
    if (slot.ReassemblyId != work.ReassemblyId) continue;      // the slot was reused
    ```
  - 만약 연결 A의 메시지가 조립 완료되어 지연 배달 큐에 등록된 후 `DrainToApplication`이 실행되기 전에 연결 A가 종료/회수(`ReclaimConnection`)되어 슬롯이 반환되고, 직후 연결 B가 동일한 슬롯 인덱스에 동일한 `ReassemblyId`로 새 메시지를 수신하여 조립을 완료한 경우, `DrainToApplication`은 연결 태그 불일치를 알아채지 못하고 연결 B의 슬롯을 연결 A의 큐 작업으로서 배달한 뒤 `_arena.Release(slot)` 및 `_pool.Return(lease)`로 슬롯과 버퍼를 조기 파괴합니다.
- **재현 방법**:
  1. 연결 A(`ConnectionTag = 0x100`)에서 `ReassemblyId = 1`인 메시지를 전송하여 조립을 완료합니다. `_completionTrigger.FileDelivery`가 호출되어 `_deferredWork`에 `(SlotIndex = 0, ConnectionTag = 0x100, ReassemblyId = 1, ...)` 작업이 적립됩니다.
  2. `Poll()`이 호출되어 `DrainToApplication`이 수행되기 전에, `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0x100)`을 호출하여 연결 A를 회수합니다. 슬롯 0은 `Free` 상태가 됩니다.
  3. 연결 B(`ConnectionTag = 0x200`)에서 `ReassemblyId = 1`인 메시지의 모든 조각을 수신합니다. 슬롯 0이 연결 B에 할당되어 조립 완료(`Open`) 상태가 됩니다.
  4. `Delivery.DrainToApplication(sink)`를 호출합니다.
  5. 큐에서 연결 A의 작업이 꺼내지지만, 슬롯 0의 상태가 `Open`이고 `ReassemblyId == 1`이므로 연결 태그 검사 없이 통과하여 연결 B의 페이로드가 배달되고 슬롯 0이 즉시 `Release` 및 버퍼 반환됩니다. 연결 B의 재조립 상태는 파괴됩니다.
- **확신도**: 확신

### 3. `FragmentOffsetBoundsFragment.Evaluate`의 도달 불가능한 초과 검사 분기 (`offset + expected > total`)
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  - `FragmentOffsetBoundsFragment.cs:54-57`에는 다음과 같은 범위 검사가 존재합니다:
    ```csharp
    if (offset + expected > total)
    {
        return Verdict<FragmentPlacementRecord>.Reject(DropReason.FragmentOffsetOutOfBounds, connectionTag, tick);
    }
    ```
  - 그러나 48-52행에서 `arrivedPayloadLengthBytes != expected`를 이미 검사하여 불일치 시 거절하고 있습니다. `expected`는 `FragmentationHeaderRecord.ExpectedPayloadLengthBytes` 프로퍼티에서 `int remaining = (int)TotalLengthBytes - offset; return remaining < uniform ? remaining : uniform;`으로 계산됩니다.
  - `offset < total`인 상태에서 `expected`는 정의상 항상 `total - offset` 이하이므로, `offset + expected`는 수학적으로 `total`을 초과할 수 없습니다. 따라서 54행의 조건문은 항상 `false`이며 56행의 반환문은 도달 불가능한 죽은 코드입니다.
- **재현 방법**:
  - `offset < total`이고 `header.FindDeclaredInvariantViolation() == DropReason.None`인 임의의 입력에 대해:
    - `arrivedPayloadLengthBytes != expected`이면 51행에서 `FragmentPayloadLengthMismatch`로 반환됩니다.
    - `arrivedPayloadLengthBytes == expected`이면 항상 `offset + expected <= total`이므로 54행의 `if` 내부(56행)는 절대 실행되지 않습니다.
- **확신도**: 확신

### 4. `DatagramOpenPipeline.OpenDatagram`에서 1단계 길이 검증 후 2단계 `TryParse` 실패 분기의 도달 불가능성
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96` (대조: `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72`, `src/Security/Records/SealedDatagramHeaderRecord.cs:62-73`)
- **무엇이 어긋나는가**:
  - `DatagramOpenPipeline.OpenDatagram`의 93-96행은 2단계 파싱 실패 검사를 수행합니다:
    ```csharp
    if (!SealedDatagramHeaderRecord.TryParse(datagram, out var header))
    {
        return Refuse(DropReason.SealedDatagramLengthOutOfRange, connectionTag, tick, 0U);
    }
    ```
  - `SealedDatagramHeaderRecord.TryParse`는 오직 `source.Length < WireBytes` (24 바이트)일 때만 `false`를 반환합니다.
  - 하지만 `OpenDatagram`의 1단계(68-72행)에서 `if (datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes ...)`를 이미 검사하여 `MinSealedDatagramBytes` (53 바이트) 미만의 데이터그램은 모두 거절하고 반환합니다.
  - 따라서 93행에 도달하는 모든 데이터그램은 길이가 최소 53 바이트 이상이므로 `source.Length < 24`는 항상 거짓이며, `TryParse`는 항상 `true`를 반환하므로 95행의 거절 분기는 결코 실행될 수 없는 죽은 코드입니다.
- **재현 방법**:
  - `datagram.Length < 53`인 입력은 68~72행에서 먼저 거절되어 93행에 도달하지 못합니다.
  - 93행에 도달하는 모든 입력은 `datagram.Length >= 53 > 24`이므로 `SealedDatagramHeaderRecord.TryParse`가 항상 `true`를 반환하여 95행은 실행되지 않습니다.
- **확신도**: 확신
