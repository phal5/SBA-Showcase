### 1. `ReassemblyDeliveryPipeline.DrainToApplication`에서 재사용된 슬롯 검증 시 `ConnectionTag` 불일치 미확인
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:51` 및 `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:11` (`DEVIATIONS.md:40` 참고)
- **무엇이 어긋나는가**:
  - `DEVIATIONS.md` 40행 및 `ReassemblyArenaResource`는 슬롯의 고유 식별자가 `(ConnectionTag, ReassemblyId)` 쌍이어야 다른 연결의 슬롯 침범을 막을 수 있다고 진술하고 있으며, 지연 배달 작업 레코드 `DeferredReassemblyDeliveryRecord`에도 `ConnectionTag` 필드가 포함되어 있습니다.
  - 그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 큐에서 꺼낸 작업 항목의 슬롯이 회수 후 다른 용도로 재사용되었는지 확인할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag != work.ConnectionTag`를 검사하지 않습니다.
  - 슬롯이 회수된 후 다른 연결에 할당되고 우연히 동일한 `ReassemblyId`를 가진 경우, 다른 연결의 슬롯이 잘못 전달되고 즉시 `_arena.Release(slot)`로 해제됩니다.
- **재현 방법**:
  1. 연결 A가 `ReassemblyId = 1`인 메시지를 완성하여 `ReassemblyCompletionTrigger.FileDelivery`가 호출되어 작업 큐에 `(slotIndex = k, ConnectionTag = A, ReassemblyId = 1)`이 등록됩니다.
  2. 배달 파이프라인이 돌기 전에 연결 A가 종료되어 `ConnectionReassemblyReclamationPipeline.ReclaimConnection(A)`가 슬롯 $k$를 회수/해제합니다.
  3. 연결 B가 새 메시지 수신을 시작하여 슬롯 $k$를 할당받고, 우연히 같은 `ReassemblyId = 1`을 가지며 메시지를 완성합니다.
  4. 다음 폴링에서 `DrainToApplication`이 연결 A의 작업 항목을 꺼내 슬롯 $k$를 검사하면, `slot.State == Open`이고 `slot.ReassemblyId == 1`이므로 검사를 통과하여 연결 B의 슬롯 데이터를 연결 A의 작업 항목 처리 흐름에서 배달 처리하고 슬롯 $k$를 해제합니다.
  5. 이후 연결 B의 정상적인 작업 항목이 큐에서 꺼내졌을 때는 슬롯 $k$가 이미 해제되었거나 또 다른 연결로 넘어가 있어 배달이 실패하거나 손상됩니다.
- **확신도**: 확신

### 2. `DatagramOpenPipeline.OpenDatagram`의 `SealedDatagramHeaderRecord.TryParse` 실패 분기 도달 불가능
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96` 및 `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72`
- **무엇이 어긋나는가**:
  - `DatagramOpenPipeline.OpenDatagram`의 1단계(68행)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes`(53 B) 조건을 검사하여 미달 시 조기 반환합니다.
  - 따라서 2단계(93행)에 도달한 `datagram`의 길이는 최소 53바이트 이상임이 보장됩니다.
  - `SealedDatagramHeaderRecord.TryParse`는 길이가 `WireBytes`(24 B) 미만일 때만 `false`를 반환하므로, 93행의 `if (!SealedDatagramHeaderRecord.TryParse(datagram, out var header))` 조건은 절대로 참이 될 수 없는 죽은 코드입니다.
- **재현 방법**: 68행의 최소 길이 검사(53 B)를 통과한 임의의 바이트 배열을 `OpenDatagram`에 전달하면 93행의 `TryParse`는 항상 `true`를 반환하므로, 94~96행의 거절 분기로 진입시키는 입력은 존재하지 않습니다.
- **확신도**: 확신

### 3. `DatagramOpenPipeline.OpenDatagram`에서 `slot == EpochSlotCode.Next` 시 재생 창 검사 실패 분기 도달 불가능
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:135` 및 `src/Security/Pipelines/DatagramOpenPipeline.cs:128`
- **무엇이 어긋나는가**:
  - `slot == EpochSlotCode.Next`인 경우 128행에서 `window`가 `ReplayWindowRecord.Empty`로 지정됩니다.
  - `ReplayWindowFragment.Evaluate`는 `!window.HasAccepted`이면 무조건 `ReplaySequenceVerdict.Fresh`를 반환합니다.
  - 따라서 `slot == EpochSlotCode.Next`일 때 `replayVerdict`는 항상 `Fresh`이며, 133행의 `if (replayVerdict != ReplaySequenceVerdict.Fresh)` 조건은 절대 참이 될 수 없습니다. 그 결과 135행의 `if (slot == EpochSlotCode.Next) key.Dispose();`는 도달할 수 없는 죽은 코드입니다.
- **재현 방법**: `EpochAdmissionFragment.Evaluate`에서 `EpochSlotCode.Next`로 판정되는 임의의 유효한 다음 시대 데이터그램을 전달하면, `window`가 항상 `Empty`이므로 `replayVerdict`는 항상 `Fresh`가 되어 135행이 실행되지 않습니다.
- **확신도**: 확신

### 4. `FragmentReceivePipeline.OpenSlot`의 버퍼 대여 유효성 검사 실패 분기 도달 불가능 및 오류 사유 불일치
- **유형**: 죽은 코드 / 자기모순
- **어디**: `src/Assembly/Pipelines/FragmentReceivePipeline.cs:199-203` 및 `src/Assembly/Pipelines/FragmentReceivePipeline.cs:170-175` (`src/Stubs/BufferPoolResource.cs:55-64,66-90` 참고)
- **무엇이 어긋나는가**:
  - `FragmentReceivePipeline.OpenSlot`은 170행에서 `BufferPoolResource.TierFor(totalLength)`를 통해 단일 대여 상한(`MaxBufferLeaseBytes`)을 이미 검증하고 초과 시 `BufferLeaseAboveSingleLeaseCap`으로 거절합니다.
  - 198행의 `_pool.Borrow(totalLength)`는 유효한 티어에 대해 항상 유효한 `BufferLeaseRecord`를 반환하며, 내부 실패 시 예외를 발생시키지 유효하지 않은 핸들을 반환하지 않습니다.
  - 따라서 199행의 `if (!_pool.IsValid(lease))`는 도달할 수 없습니다. 또한 설령 도달하더라도 이미 170행에서 크기를 검증했음에도 거절 사유를 `BufferLeaseAboveSingleLeaseCap`으로 반환하는 것은 사유의 의미와도 모순됩니다.
- **재현 방법**: 170행의 단일 대여 상한 검사를 통과한 임의의 조각 헤더를 수신 파이프라인에 전달하여 슬롯을 열게 하면, 198행에서 반환된 리스는 항상 `_pool.IsValid(lease) == true`이므로 199~203행의 보상 트랜잭션 및 거절 분기로 진입하지 않습니다.
- **확신도**: 확신
