## 결점

### 1. `SealedDatagramIntake.Dispose` 호출 시 소유/래핑한 `ReassemblyTable`을 닫지 않아 자원 누수 발생
- **유형**: 자원 누수
- **어디**: `src/Realtime.Assembly/DatagramSecurity/SealedDatagramIntake.cs:94-100` 및 `src/Realtime.Assembly/MessageAssembly/ReassemblyTable.cs:194-203`
- **무엇이 어긋나는가**: `SealedDatagramIntake`는 수신 계층의 진입점으로서 생성자에서 `ReassemblyTable`을 주입받아 관리하며 `IDisposable`을 구현한다. 그러나 `SealedDatagramIntake.Dispose()`는 `_opener.Dispose()`와 평문 버퍼 소거만 수행하고 `_table.Close()`를 호출하지 않는다. 수신 파이프라인(`Intake`)을 종료하는 호출자가 `Table.Close()`를 별도로 호출하지 않으면, 진행 중이던 조립 건에 할당된 `BufferPool` 버퍼 대여(`BufferLease`) 및 `ReassemblyBudget`의 연결별/전역 예산 점유가 해제되지 않고 영구 누수된다.
- **재현 방법**:
  1. `Rig.Create()`로 리그를 생성하고 `peer = rig.NewConnection()`을 생성한다.
  2. 미완성 메시지의 조각 1개를 `peer.Intake.Offer(...)`로 전달하여 컨텍스트가 열리게 한다 (`peer.Table.InProgress == 1`, `rig.Pool.OutstandingLeases == 1`, `rig.Global.Bytes > 0`).
  3. `peer.Intake.Dispose()`를 호출한다.
  4. `peer.Table`이 닫히지 않아 `rig.Pool.OutstandingLeases`가 1로 남아 버퍼가 누수되고 `rig.Global.Bytes`가 0으로 회수되지 않는다.
- **확신도**: 확신

### 2. 한 시대 분량의 패킷이 전멸하면 수신측 `DatagramOpener`가 영구 불능 상태에 빠짐
- **유형**: 미강제 불변식
- **어디**: `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:136-159`
- **무엇이 어긋나는가**: `DatagramOpener`는 현재 시대(`_current.Epoch`), 유예 중인 직전 시대(`_previous.Epoch`), 바로 다음 시대(`_next.Epoch = _current.Epoch + 1`)의 3개 시대만 유효한 시대로 인식한다. 연속된 패킷 유실이나 일시적 네트워크 단절로 인해 송신측에서 한 시대(16 MiB 또는 60초) 동안 보낸 데이터그램이 수신측에 하나도 도착하지 못하고 그 다음 시대(`_current.Epoch + 2`)의 패킷이 처음 도착하면, `DatagramOpener.TryOpen`은 이를 `DropReason.UnknownEpoch`로 거절한다. 이후 수신측은 시대를 전진시킬 수단이 전혀 없어 이후의 모든 패킷(시대 >= 2)이 영구히 거절되며 연결이 영구 불능 상태가 된다.
- **재현 방법**:
  1. 동일 마스터 비밀과 연결 ID로 `DatagramSealer`와 `DatagramOpener`를 생성한다.
  2. `sealer`에서 `EpochDurationMs`(60,000ms) 경과 후 패킷을 보내지 않고 추가로 60,000ms를 더 전진시킨 뒤 패킷을 봉인하여 시대 번호를 2(`sealer.Epoch == 2`)로 만든다.
  3. 해당 데이터그램을 `opener`(`CurrentEpoch == 0`, `_next.Epoch == 1`)의 `TryOpen`에 전달한다.
  4. `TryOpen`은 `false`를 반환하고 `reason`은 `DropReason.UnknownEpoch`가 되며, 이후 송신측이 보내는 모든 데이터그램이 영구히 거절된다.
- **확신도**: 확신

### 3. 나가는 쪽 상한이 낮아진 후에도 이전 계획(`FragmentPlan`)을 재사용한 상한 초과 송신 미차단
- **유형**: 미강제 불변식
- **어디**: `src/Realtime.Assembly/Stubs/PathLimits.cs:126-136` 및 `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:150-198`
- **무엇이 어긋나는가**: `PathLimits.LowerOutbound`는 나가는 쪽 상한을 낮추지만, `MessageSplitter.WriteFragment`는 `FragmentPlan`과 `DatagramSealer`만 인자로 요구하며 현재 연결의 `PathLimits`나 상한 세대 번호를 검증하지 않는다. 호출자가 상한이 낮아지기 전에 수립된 `FragmentPlan`을 재사용하여 `WriteFragment`를 호출하면, 현재 낮아진 상한을 초과하는 크기의 대형 데이터그램이 아무런 제약 없이 봉인되어 송신된다.
- **재현 방법**:
  1. `limits = new PathLimits(options, 1452, 1200)`을 생성한다.
  2. `splitter.TryPlan(40_000, limits, out plan, out _)`으로 1,452 B 기준 분할 계획을 수립한다.
  3. `limits.LowerOutbound(1200)`을 호출하여 나가는 상한을 1,200 B로 낮춘다.
  4. 이전 `plan`을 넘겨 `splitter.WriteFragment(plan, ..., destination)`을 호출한다.
  5. 1,452 B 크기의 데이터그램이 오류 없이 생성·봉인되어 반환된다.
- **확신도**: 확신

### 4. `MessageSplitter` 내부 스크래치 버퍼(`_frameScratch`) 공유로 인한 동시 호출 시 평문 오염 가능성
- **유형**: 미강제 불변식
- **어디**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:82-89` 및 `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:185-194`
- **무엇이 어긋나는가**: `MessageSplitter`는 여러 연결이 인스턴스를 공유하도록 설계되었으나, 조각 프레임 작성을 위해 단일 필드 `byte[] _frameScratch`를 사용한다. `WriteFragment`는 `_frameScratch`에 헤더와 페이로드를 복사하고 봉인한 뒤 `ZeroMemory`로 지우는데, 멀티스레드 또는 비동기 환경에서 둘 이상의 호출자가 `WriteFragment`를 동시에 호출할 경우 `_frameScratch` 내용이 덮어써지거나 0으로 소거되어 잘못된 평문이 암호화되거나 데이터 손상이 발생한다.
- **재현 방법**:
  1. 단일 `MessageSplitter` 인스턴스를 생성한다.
  2. 별도의 두 스레드에서 서로 다른 메시지 바이트를 전달하며 `WriteFragment`를 동시에 호출한다.
  3. `_frameScratch` 경쟁 상태(Race condition)로 인해 다른 스레드의 메시지 조각이 섞여 봉인되거나 `ZeroMemory` 타이밍에 의해 손상된 데이터가 봉인된다.
- **확신도**: 확신

### 5. `PathLimits._outbound` 필드의 동기화 부재로 인한 가시성 및 경쟁 상태
- **유형**: 미강제 불변식
- **어디**: `src/Realtime.Assembly/Stubs/PathLimits.cs:30` 및 `src/Realtime.Assembly/Stubs/PathLimits.cs:126-148`
- **무엇이 어긋나는가**: `PathLimits`는 여러 모듈이 공유 참조하는 클래스이며 연결 생명주기 동안 `_outbound`가 변경될 수 있다. 그러나 `_outbound` 필드가 `volatile`이나 동기화 락 없이 단순 `int` 필드로 선언되어 있어, 한 스레드가 `LowerOutbound` 또는 `ApplyOutboundReport`로 값을 변경하더라도 다른 스레드에서 `Outbound`, `OutboundFragmentPayload` 등을 읽을 때 메모리 배리어 부재로 인해 즉각적인 가시성이 보장되지 않는다.
- **재현 방법**:
  1. `PathLimits` 인스턴스를 생성하여 한 스레드에서는 `LowerOutbound`를 호출하고 다른 스레드에서는 `OutboundFragmentPayload`를 루프에서 읽는다.
  2. 메모리 배리어가 없어 CPU 캐시 지연으로 인해 변경된 상한값이 지연 반영될 수 있다.
- **확신도**: 의심

## 결점이 아니라고 판단한 것

1. **`MaxFragmentsPerMessage = 64`의 도달 불가능한 여유 구간 (59~64조각)**
   - `M = 65,536` 및 `P_floor = 1,142`일 때 최대 도달 가능한 실제 조각 수는 58개이며 59~64는 유효한 입력으로 도달할 수 없다. 하지만 이는 64비트 도착 비트맵(`ulong`)과의 정렬 및 안전한 상계 보장을 위한 것이며, `DEVIATIONS.md` §2-(1) 및 하네스 검사 2에서 의도된 설계임을 명시적으로 밝히고 있어 결점이 아니다.

2. **들어오는 쪽 최악치 `WorstCaseInboundFootprint`가 연결 상한이 아닌 `DatagramFloorBytes` 기준으로 계산되는 점**
   - 연결의 수신 상한이 1,452 B로 설정되어 있더라도 피어가 경로 사정상 1,200 B로 잘게 쪼개어 전송할 수 있는 정당한 트래픽을 허용하기 위해 `MaxInboundFragments = ⌈M / (D_floor - H)⌉ = 58`을 기준으로 예산을 산정한다. 이는 `ASYMMETRY-NOTES.md` §5-1에 명시된 의도된 설계이다.

3. **크기 초과 시 `InboundDatagramTooLarge`와 역산된 P 초과 시 `FragmentInconsistent`로 사유가 나뉘는 점**
   - 데이터그램 헤더 파싱 전 길이 검사 단계와 파싱 후 필드 정합성 검증 단계의 계층 분리에 따른 것으로 `ASYMMETRY-NOTES.md` §5-6에서 사유를 분리한 근거를 밝히고 있으므로 결점이 아니다.

4. **`ReassemblyTable.Offer`의 `FreeSlot() < 0` 방어 분기**
   - `_budget.TryReserve`에서 이미 `ContextLimit`(= `_slots.Length`)을 검사하므로 정상 상태에서는 도달하지 않으나, 설정 변경이나 방어적 프로그래밍을 위한 분기이므로 결점이 아니다.

5. **`DatagramOpener`의 시대 번호 `2^32` 오버플로**
   - 60초 주기 기준 약 8,000년이 소요되어 현실적인 연결 수명 내에 도달하지 않으며 `EXTENSION-NOTES.md` §5-2에서 가정을 명시하고 있으므로 결점이 아니다.
