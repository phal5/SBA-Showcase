## 결점

### 1. `ReassemblyDeliveryPipeline`에서 슬롯 재사용 검증 시 `ConnectionTag` 누락으로 인한 타 연결 슬롯 오인 및 조기 반납
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:51` 및 `src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:16`
- **무엇이 어긋나는가**: 
  `DEVIATIONS.md`(40행)에서는 재조립 슬롯의 식별 키를 `(연결 태그, ReassemblyId)` 복합 키로 정의하였고, 완료 작업 큐에 들어가는 `DeferredReassemblyDeliveryRecord` 구조체(16행) 역시 `ConnectionTag`와 `ReassemblyId`를 모두 보관하도록 선언되어 있습니다.
  그러나 `ReassemblyDeliveryPipeline.DrainToApplication`의 슬롯 재사용 검증(51행)에서는 `if (slot.ReassemblyId != work.ReassemblyId) continue;`만 검사하고, `slot.ConnectionTag != work.ConnectionTag` 검사를 누락했습니다.
  특정 슬롯 인덱스가 완성 후 지연 큐에 등록된 상태에서 연결 해제/만료 등으로 반납된 뒤, 다른 연결이 동일한 슬롯 인덱스에 우연히 동일한 `ReassemblyId`로 재할당받아 조립을 완료한 경우, 파이프라인은 해당 슬롯이 다른 연결의 것임을 인지하지 못하고 다른 연결의 슬롯을 대상으로 배달 처리 및 `_arena.Release(slot)` / `_pool.Return(lease)`을 실행하여 슬롯 상태 불일치 및 버퍼 조기 반납을 일으킵니다.
- **재현 방법**:
  1. 연결 A(`tag = 0xA`)가 `ReassemblyId = 1`로 슬롯 0을 할당받아 모든 조각을 수신하고 완성되어 `_deferredWork`에 작업 항목 `(slotIndex: 0, tag: 0xA, reassemblyId: 1)`이 등록됨.
  2. `DrainToApplication`이 실행되기 전에 연결 A가 종료되어 `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0xA)`이 호출되고 슬롯 0이 회수됨.
  3. 즉시 연결 B(`tag = 0xB`)가 `ReassemblyId = 1`로 슬롯 0을 할당받아 조립을 완료함.
  4. 이후 `DrainToApplication`이 연결 A의 작업 항목을 꺼낼 때, `slot.State == Open` 및 `slot.ReassemblyId == 1` 검사를 모두 통과하므로 연결 B의 슬롯 0 데이터를 읽어 전달하고, 연결 B의 슬롯 0과 버퍼 리스를 즉시 반납(`Release`/`Return`)해 버림. 연결 B의 정당한 완성 작업 항목이 나중에 처리될 때는 이미 슬롯이 해제되어 배달이 누락되거나 이중 해제가 발생함.
- **확신도**: 확신

### 2. `FragmentOffsetBoundsFragment.Evaluate` 내 `offset + expected > total` 조건문의 불필요한 도달 불가능 분기
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  `FragmentOffsetBoundsFragment.Evaluate`의 43행에서 `if (offset >= total)`을 먼저 검사하므로 48행 이후 시점에서는 항상 `offset < total` (즉 `total - offset > 0`)임이 보장됩니다.
  48행에서 계산되는 `header.ExpectedPayloadLengthBytes`는 내부적으로 `remaining = total - offset`, `expected = remaining < uniform ? remaining : uniform`으로 구현되어 항상 `expected <= total - offset` (즉 `offset + expected <= total`)을 반환합니다.
  따라서 54행의 `if (offset + expected > total)` 조건은 수학적으로 항등적으로 거짓(false)이며, 해당 분기 블록은 어떤 입력에서도 절대 실행될 수 없는 죽은 코드입니다.
- **재현 방법**:
  합법적인 `FragmentationHeaderRecord`와 `arrivedPayloadLengthBytes`를 전달하여 43행(`offset >= total`)과 49행(`arrivedPayloadLengthBytes != expected`)을 통과시키더라도, `expected`의 정의에 의해 `offset + expected`는 항상 `total` 이하가 되므로 54행의 `Reject(FragmentOffsetOutOfBounds)`는 재현할 수 없습니다.
- **확신도**: 확신

### 3. `EngineConstantsRecord.FindViolatedConstantRelation` 내 X7 관계식의 부호 있는 64비트 정수(`long.MaxValue`) 사용
- **유형**: 계산 오류
- **어디**: `src/Stubs/EngineConstantsRecord.cs:359` vs `src/Security/Resources/SendSecurityAssociationResource.cs:61` 및 `EXTENSION-NOTES.md:191`
- **무엇이 어긋나는가**:
  `SendSecurityAssociationResource.NextSequence`는 `ulong` 타입이며 순번 공간의 고갈 여부는 `NextSequence == ulong.MaxValue` ($2^{64}-1$)로 판정합니다. 주석 및 `EXTENSION-NOTES.md` §5.4에서도 순번 공간을 $2^{64}$로 진술하고 있습니다.
  그러나 `FindViolatedConstantRelation()`의 X7 관계식(359행)에서는 `long.MaxValue` ($2^{63}-1$)를 사용하여 $2^{64}$가 아닌 부호 있는 64비트 상한을 기준으로 바이트 한도를 검사하고 있습니다.
- **재현 방법**:
  `EpochByteLimit`을 `long.MaxValue / 53` 이상 `ulong.MaxValue / 53` 미만의 값으로 설정할 경우, 실제 $2^{64}$ 순번 공간 내에서는 안전함에도 불구하고 시작 시점 상수 관계 검사(X7)에서 거짓 위반(false positive)을 반환하며 시작이 거부됩니다.
- **확신도**: 의심
