## 결점
### 1. `ReassemblyDeliveryPipeline`이 지연 작업 처리 시 슬롯 재사용 검사에서 `ConnectionTag` 불일치를 검사하지 않아 타 연결 슬롯 오해제 및 잘못된 배달 위험
- **유형**: 미강제 불변식 / 자원 누수
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:49-58` 및 `DEVIATIONS.md:39-43`
- **무엇이 어긋나는가**: `DEVIATIONS.md` 39~43행은 `ReassemblyId`가 전역이 아닌 연결별(`ConnectionTag, ReassemblyId`) 격리 단위임을 명시하고 있으나, `ReassemblyDeliveryPipeline.DrainToApplication`은 적립된 지연 작업(`work`)을 처리할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고 `slot.ConnectionTag != work.ConnectionTag`를 검사하지 않습니다. 연결 A의 재조립 완료 후 배달 전(동일 폴 내 또는 지연 중)에 연결 A가 회수(`ReclaimConnection`)되고 동일 슬롯에 동일 `ReassemblyId`를 쓰는 연결 B의 새 재조립이 할당된 경우, 연결 B의 슬롯을 연결 A의 것으로 오인하여 연결 B의 미완성/완성 슬롯을 조기 해제(`_arena.Release(slot)`, `_pool.Return(lease)`)하고 메모리를 파괴하는 치명적인 상호 간섭이 발생합니다.
- **재현 방법**:
  1. 연결 `0xAA`에서 `reassemblyId = 1` 메시지의 모든 조각을 수신하여 `ReassemblyCompletionTrigger.FileDelivery`를 유발합니다 (`DeferredReassemblyDeliveryRecord(SlotIndex=0, ConnectionTag=0xAA, ReassemblyId=1)` 적립).
  2. `Delivery.DrainToApplication`이 호출되기 전에 `Reclamation.ReclaimConnection(0xAA)`를 호출하여 슬롯 0을 회수합니다.
  3. 연결 `0xBB`에서 `reassemblyId = 1` 메시지의 첫 조각을 전송하여 회수된 슬롯 0을 재할당받게 합니다 (`slot.ConnectionTag = 0xBB, slot.ReassemblyId = 1`).
  4. `Delivery.DrainToApplication(sink)`를 호출합니다.
  5. `DrainToApplication`은 `slot.ReassemblyId == work.ReassemblyId (1 == 1)`만 확인하고 `ConnectionTag` 불일치(`0xBB != 0xAA`)를 감지하지 않아 연결 B의 슬롯 0에 대해 배달 및 `_arena.Release(slot)`, `_pool.Return(lease)`를 실행하여 연결 B의 활성 슬롯과 버퍼를 임의로 파괴합니다.
- **확신도**: 확신

### 2. `ReassemblyProgressRecord`의 기본값(`default`)에서 `IsComplete`가 `true`로 평가되어 완료 판정 불변식을 우회할 수 있음
- **유형**: 미강제 불변식 / 계산 오류
- **어디**: `src/Assembly/Records/ReassemblyProgressRecord.cs:25` 및 `src/Assembly/Records/ReassembledMessageRecord.cs:8-13` / `src/Assembly/Records/ReassemblyProgressRecord.cs:5-8`
- **무엇이 어긋나는가**: `ReassemblyProgressRecord.cs`와 `ReassembledMessageRecord.cs`는 "완성 판정(`IsComplete == true`) 없이는 `ReassembledMessageRecord`가 생성될 수 없다"는 불변식을 선언하고 있으나, `ReassemblyProgressRecord.IsComplete`가 `ArrivedFragmentCount == FragmentCount`로만 구현되어 있어 기본 구조체 값 `default(ReassemblyProgressRecord)`(두 필드 모두 0)에서 `0 == 0`이 되어 `true`가 반환됩니다. 이로 인해 `FragmentReceiveOutcome.Dropped` 등으로 생성된 기본 진행 상태에서도 `IsComplete`가 참이 되며, `ReassembledMessageRecord.TryCreate(default, ...)`를 호출하면 `FragmentCount = 0`인 비정상 메시지 레코드가 생성되어 불변식이 깨집니다. 올바른 식은 `FragmentCount > 0 && ArrivedFragmentCount == FragmentCount`여야 합니다.
- **재현 방법**:
  ```csharp
  ReassemblyProgressRecord def = default;
  // def.IsComplete를 확인하면 true가 반환됨
  var pool = new BufferPoolResource();
  var lease = pool.Borrow(1024);
  bool created = ReassembledMessageRecord.TryCreate(default, pool, lease, 0x1, 1, 100, out var msg);
  // created는 true를 반환하고 FragmentCount가 0인 ReassembledMessageRecord가 생성됨
  ```
- **확신도**: 확신

### 3. `FragmentOffsetBoundsFragment.Evaluate`의 `offset + expected > total` 조건이 항상 거짓인 도달 불가능한 죽은 코드임
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**: 43행의 `if (offset >= total)` 검사를 통과하면 `total - offset > 0`입니다. 48행의 `expected`는 `header.ExpectedPayloadLengthBytes`에서 `Math.Min(total - offset, uniform)`으로 계산되므로 항상 `expected <= total - offset` (즉, `offset + expected <= total`)이 수학적으로 보장됩니다. 따라서 54행의 `if (offset + expected > total)` 조건문과 56행의 `FragmentOffsetOutOfBounds` 거절 반환문은 어떤 입력에서도 절대 실행될 수 없는 죽은 코드입니다.
- **재현 방법**:
  어떤 `FragmentationHeaderRecord`와 페이로드 길이를 전달하더라도, 43행(`offset >= total`)과 49행(`arrived != expected`)을 통과한 경우 `offset + expected <= total`이 항진 성립하므로 54~57행 분기는 실행할 수 없습니다. (재현 불가 / 도달 불가능)
- **확신도**: 확신

### 4. `FragmentReceivePipeline.OpenSlot`의 버퍼 대여 검증 실패 및 보상 분기가 항상 거짓인 죽은 코드임
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Pipelines/FragmentReceivePipeline.cs:199-203`
- **무엇이 어긋나는가**: `BufferPoolResource.Borrow`는 유효하지 않은 요청 크기에는 예외를 던지며, 정상 반환 시에는 항상 유효한 `BufferLeaseRecord`를 반환합니다. `BufferPoolResource.IsValid(lease)`는 `Borrow`가 반환한 직후의 유효한 레코드에 대해 항상 `true`를 반환하므로, `OpenSlot` 199행의 `if (!_pool.IsValid(lease))` 조건은 항상 거짓이며 201~202행의 보상 트랜잭션(`_arena.CancelReservation`) 및 거절 반환 코드는 실행되지 않는 죽은 코드입니다.
- **재현 방법**:
  `OpenSlot`을 실행하는 어떤 입력에서도 `_pool.Borrow` 호출 직후 `!_pool.IsValid(lease)`가 참이 되는 상태를 만들 수 없으므로 200~203행은 실행되지 않습니다. (재현 불가 / 도달 불가능)
- **확신도**: 확신

### 5. `DatagramOpenPipeline.OpenDatagram`의 `SealedDatagramHeaderRecord.TryParse` 실패 분기가 도달 불가능한 죽은 코드임
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:93-96`

- **확신도**: 확신
