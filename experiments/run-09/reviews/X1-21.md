## 결점

### 1. `Program.cs` 클래스 주석의 검사 수 불일치
- **유형**: 자기모순
- **어디**: `harness/Program.cs:22` 및 `harness/Program.cs:42-65`
- **무엇이 어긋나는가**: `harness/Program.cs:22`의 클래스 문서 주석에는 `Fifteen checks, each printing PASS or FAIL with numbers`라고 검사가 15개로 기술되어 있으나, 실제 `Program.cs` 코드(`checks` 배열 42~65행)에는 21개의 검사(`Check01` ~ `Check21`)가 정의되어 실행됩니다. 보안 확장 시점(검사 1~15)에서 비대칭 경로 한도 확장 시점(검사 16~21 추가)으로 넘어오면서 헤더 주석의 검사 개수가 갱신되지 않았습니다.
- **재현 방법**: `harness/Program.cs` 22행 주석의 `Fifteen checks` 문구와 42~65행의 `checks` 배열 내 원소 수(21개)를 대조합니다. `dotnet run` 실행 시 `all 21 checks passed`가 출력됩니다.
- **확신도**: 확신

### 2. `FragmentOffsetBoundsFragment` 내 도달 불가능한 초과 검사 분기
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**: 43행에서 `if (offset >= total)`을 거절하고, 49행에서 `arrivedPayloadLengthBytes != expected`를 거절한 후, 54행에서 `if (offset + expected > total)`을 다시 검사합니다. 그러나 `expected`는 `FragmentationHeaderRecord.ExpectedPayloadLengthBytes`에서 `remaining = total - offset`에 대해 `remaining < uniform ? remaining : uniform`으로 계산됩니다. 43행을 통과한 시점에서 `offset < total`이므로 `remaining > 0`이며, `expected <= remaining = total - offset`이 수학적으로 항상 성립합니다. 따라서 `offset + expected <= total`이 항상 보장되므로 54행의 `offset + expected > total` 분기는 어떠한 입력으로도 도달할 수 없는 죽은 코드입니다.
- **재현 방법**: `FragmentationHeaderRecord`의 `TotalLengthBytes`, `FragmentCount`, `FragmentIndex`에 어떠한 유효한 값을 설정하더라도, 43행(`offset >= total`)과 49행(`arrived != expected`)을 통과한 경우 54행의 조건식 `offset + expected > total`은 항상 `false`가 되어 56행의 `Verdict.Reject`에 도달하지 못합니다.
- **확신도**: 확신
