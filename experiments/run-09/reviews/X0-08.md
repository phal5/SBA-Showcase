## 결점

### 1. `EngineOptions.Validate()` 내 K9 검사 조건의 항진성 (항상 참인 잉여 조건)
- **유형**: 죽은 코드 / 항상 참이거나 항상 거짓인 조건
- **어디**: `src/Realtime.Assembly/Stubs/EngineOptions.cs:245-246`
- **무엇이 어긋나는가**:
  - `EngineOptions.Validate()` 214행에서 `DatagramMaxBytes >= DatagramFloorBytes`를 강제하고, 240행에서 K4(`(long)MaxFragmentsPerMessage * FragmentPayloadFloor >= MaxMessageBytes`)를 강제합니다.
  - `FragmentPayloadCeiling`은 `DatagramMaxBytes - FragmentOverheadBytes`이고 `FragmentPayloadFloor`는 `DatagramFloorBytes - FragmentOverheadBytes`이므로, 앞선 두 검사를 통과하면 필연적으로 `FragmentPayloadCeiling >= FragmentPayloadFloor > 0`이 성립합니다.
  - 따라서 245행의 `(long)MaxFragmentsPerMessage * FragmentPayloadCeiling >= MaxMessageBytes` 조건은 214행과 240행이 참인 한 수학적으로 항상 참이 되며, 결코 `false`가 되어 예외를 던질 수 없는 도달 불가능한 검사 분기입니다.
  - K9("경로가 상한까지 올라가도 K3·K4가 유지될 것")의 실제 관계 검사는 251~252행의 `RequireRelationsFor`에서 `D_max`에 대해 `FragmentsForDatagram(DatagramMaxBytes) <= MaxFragmentsPerMessage`로 완전하게 수행되고 있으므로 245행은 의미 없는 중복 조건문입니다.
- **재현 방법**:
  `DatagramFloorBytes = 1200`, `DatagramMaxBytes = 1452`, `MaxMessageBytes = 65536`, `MaxFragmentsPerMessage = 64` 등 214행(`D_max >= D_floor`) 및 240행(K4)을 만족하는 모든 설정값 조합에서 245행의 조건은 항상 `true`로 평가되어 해당 `Require`의 실패 분기(예외 발생)에 도달할 수 없습니다. 반대로 245행을 실패(`false`)하게 만들려면 `FragmentPayloadCeiling < FragmentPayloadFloor`이거나 K4가 거짓이어야 하는데, 이는 이미 선행 검사(214행 또는 240행)에서 먼저 걸려 예외가 발생하므로 245행이 단독으로 위반을 감지하는 입력은 존재하지 않습니다.
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`MessageSplitter.TryPlan`의 조각 수 상한 검사 (`totalFragments > MaxFragmentsPerMessage`)**
   - `EngineOptions.Validate()`를 거친 유효한 설정에서는 `totalFragments <= FragmentsForDatagram(D_floor) = 58 <= 64`이므로 정상 경로에서는 도달하지 않는 분기입니다.
   - 그러나 이는 `Validate()` 검증을 거치지 않고 직접 생성된 옵션 객체가 주입되거나 런타임 불변식이 깨졌을 때 조용히 오버플로되는 것을 방어하기 위한 의도적인 심층 방어(defense-in-depth) 가드이며 코드 주석에도 그 의도가 명시되어 있어 결함으로 보지 않았습니다.

2. **`ReassemblyTable.Offer`의 여유 슬롯 미발견 분기 (`FreeSlot() < 0`)**
   - `_budget.TryReserve`가 `_contexts + 1 <= ContextLimit`을 먼저 강제하므로 `_slots` 배열(크기 `N_conn`)에서 빈 슬롯을 찾지 못하는 상황은 정상적으로 발생하지 않습니다.
   - 이는 메모리 누수나 상태 불일치 시 버퍼를 즉시 반납하고 예산을 복구하도록 하는 방어적 실패 처리 경로이므로 정상적인 설계로 판단했습니다.

3. **`SealedDatagramIntake.Offer`의 `reason` 출력 인자**
   - 봉인 개봉 실패(`!_opener.TryOpen`) 또는 프레임 파싱 실패(`!FragmentHeader.TryRead`) 시에는 `reason`에 구체적인 실패 사유가 실리지만, `_table.Offer`로 위임되는 정상 개봉 경로에서는 `reason = DropReason.None`으로 설정됩니다.
   - `ReassemblyTable`은 D7의 사유들을 내부 `CounterBank`에 직접 집계하며, `SealedDatagramIntake`의 요약 주석에도 "열렸으면 그 평문에서 조각 머리말을 읽어 표에 넘긴다. 이후 판정은 D7의 것이다"라고 명시되어 있어 계층 분리 설계에 부합합니다.

4. **문서(`ASYMMETRY-NOTES.md` §5, `EXTENSION-NOTES.md` §5)에 기록된 남은 한계점들**
   - `PathLimits`의 가변 필드(`_outbound`) 멀티스레드 비안전성, 2^32 시대 번호 롤오버, 시대 유실 시 단방향 복구 불가, D4의 장기 캐싱 미강제 등은 시스템의 단순성과 단일 스레드 폴 모델 전제 하에서 의도된 트레이드오프 및 설계 한계로 문서에 투명하게 기록되어 있으므로 구현 결함이 아닙니다.
