## 결점

### 1. `MessageSplitter.WriteFragment`의 예외 매개변수 이름 불일치 및 도달 불가능한 조건 분기
- **유형**: 자기모순 / 죽은 코드
- **어디**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:186-187`
- **무엇이 어긋나는가**: 
  1. `frame`은 내부 스크래치 버퍼 `_frameScratch`에서 `frameLength = FragmentHeader.Size + payloadLength` 크기로 슬라이스된 스팬입니다. `plan.PayloadLengthAt(index)`는 항상 1 이상이므로 `frameLength`는 최소 19 B 이상입니다. `FragmentHeader.TryWrite`는 대상 스팬 길이가 18 B 이상이면 항상 성공하므로 `!header.TryWrite(frame)` 분기는 절대로 참이 될 수 없는 도달 불가능한 죽은 코드입니다.
  2. 해당 분기에서 예외를 던질 때 `nameof(datagramDestination)`을 매개변수 이름으로 지정하고 있습니다. 그러나 해당 쓰기 대상은 `datagramDestination`이 아니라 내부 프레임 버퍼 `frame`이므로, 설령 발생하더라도 호출자에게 엉뚱한 매개변수가 잘못되었다는 모순된 에러 정보를 전달합니다.
- **재현 방법**: `plan.IsValid`가 참인 모든 정상 호출 흐름에서 `frameLength >= 19`이므로 `!header.TryWrite(frame)` 분기는 어떤 입력으로도 실행되지 않습니다.
- **확신도**: 확신

### 2. `DatagramSealer.Seal`의 도달 불가능한 머리말 쓰기 검사
- **유형**: 죽은 코드
- **어디**: `src/Realtime.Assembly/DatagramSecurity/DatagramSealer.cs:97`
- **무엇이 어긋나는가**: 바로 앞 라인 90-93에서 `int length = DatagramSeal.DatagramLengthFor(plaintext.Length)` (`= 40 + plaintext.Length >= 41`)를 계산하고 `if (datagram.Length < length) throw ...`로 검사하여 이미 예외를 던집니다. 따라서 라인 97에 도달한 시점에 `datagram.Length`는 최소 41 B 이상임이 보장되며, `SealedDatagramHeader.TryWrite`가 요구하는 24 B보다 항상 큽니다. 그러므로 `if (!header.TryWrite(datagram))` 분기는 절대로 참이 될 수 없는 죽은 코드입니다.
- **재현 방법**: `plaintext.Length >= 1`인 모든 정상 입력에 대해 `datagram.Length >= 41`이 강제되므로 해당 조건 분기(`!header.TryWrite(datagram)`)는 어떤 입력으로도 도달할 수 없습니다.
- **확신도**: 확신

### 3. `ReassemblyTable.Offer`의 도달 불가능한 슬롯 고갈 분기
- **유형**: 죽은 코드
- **어디**: `src/Realtime.Assembly/MessageAssembly/ReassemblyTable.cs:118-126`
- **무엇이 어긋나는가**: 라인 104에서 `_budget.TryReserve`를 호출하여 연결별 건수 상한 `_contexts + 1 > ContextLimit` (`PerConnectionReassemblyContexts` = `_slots.Length`)을 먼저 검사합니다. 이를 통과한 경우에만 라인 118의 `FreeSlot()`에 도달하므로, `_slots` 배열에는 반드시 1개 이상의 빈 공간이 존재합니다(`FreeSlot() >= 0`). 따라서 `if (slot < 0)` 분기는 코드 주석에서도 스스로 "건수 축이 슬롯 수와 같으므로 도달 불가"라고 기술하고 있듯이 결코 실행될 수 없는 죽은 코드입니다.
- **재현 방법**: `_budget`의 `ContextLimit`과 `_slots.Length`가 동일한 설정 하에서는 어떤 조각 입력 시퀀스를 넣어도 `slot < 0` 분기에 도달하지 않습니다.
- **확신도**: 확신

### 4. `EXTENSION-NOTES.md` §3 표의 `OuterHeaderBytes` 수치 불일치
- **유형**: 중복 불일치
- **어디**: 
  - `EXTENSION-NOTES.md:88`
  - `src/Realtime.Assembly/Stubs/EngineOptions.cs:32` (및 `EXTENSION-NOTES.md:48`)
- **무엇이 어긋나는가**: `EXTENSION-NOTES.md` §3 표의 88행에서 "바깥 덧붙이의 폭 (32 → 40 B)" 항목을 설명하며 "실행: `EngineOptions.OuterHeaderBytes`(16), `EngineOptions.AeadTagBytes`(16)"라고 기술하고 있습니다. 그러나 보안 확장 후의 실제 코드(`EngineOptions.cs:32`) 및 같은 문서 §2 표(48행)에서는 `OuterHeaderBytes`가 `SealedDatagramHeader.Size`인 24 B로 정의되어 있습니다. 표 88행의 산문에 확장 전 과거 수치(16)가 잘못 남아 있어 코드 및 문서 내부 기술과 어긋납니다.
- **재현 방법**: `EXTENSION-NOTES.md` 88행의 "OuterHeaderBytes(16)"와 `EngineOptions.cs`의 `OuterHeaderBytes` 프로퍼티 반환값(24)을 대조.
- **확신도**: 확신

### 5. `EngineOptions.Validate()`의 K9 검사 조건 중복 (항상 참)
- **유형**: 죽은 코드
- **어디**: `src/Realtime.Assembly/Stubs/EngineOptions.cs:245` (대조: `EngineOptions.cs:214, 240`)
- **무엇이 어긋나는가**: `EngineOptions.Validate()`의 라인 214에서 `DatagramMaxBytes >= DatagramFloorBytes`를 검증하고, 라인 240에서 `(long)MaxFragmentsPerMessage * FragmentPayloadFloor >= MaxMessageBytes` (K4)를 검증합니다. `FragmentPayloadCeiling = DatagramMaxBytes - H >= DatagramFloorBytes - H = FragmentPayloadFloor`이므로, 앞선 두 검증을 통과한 상태에서 라인 245의 `(long)MaxFragmentsPerMessage * FragmentPayloadCeiling >= MaxMessageBytes` (K9) 검사는 수학적으로 항상 참이 되어 절대로 실패하지 않는 중복 조건입니다.
- **재현 방법**: `DatagramMaxBytes >= DatagramFloorBytes`이고 K4가 성립하는 유효한 `EngineOptions`에서 `Validate()`를 호출하면 라인 245의 조건은 항상 `true`로 평가됩니다.
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`F = 64` 도착 비트맵 상한 중 59~64의 비어 있는 값역 (도달 불가능한 여유)**
   - `P_floor = 1,142` B 하에서 최대 메시지 크기 65,536 B를 분할할 때 물리적으로 도달 가능한 최대 조각 수는 58개입니다. 59~64조각 선언은 항상 `FragmentInconsistent`로 거절됩니다.
   - 이는 원본 계획 명세의 계산 결함이나, 코드베이스 문서(`DEVIATIONS.md` §계획이 틀렸던 지점 (1))에서 이미 수학적 증명과 함께 결함임을 명시하고 하네스 검사 2에서 기계적으로 고정하여 관리하고 있으므로 새로운 결점으로 분류하지 않았습니다.

2. **`DatagramOpener.TryOpen`의 `ArgumentException` (평문 목적지 버퍼 크기 부족)**
   - `DatagramOpener.cs` 주석의 "E3 — 예외를 던지지 않는다" 원칙에도 불구하고 `plaintext.Length < bodyLength`일 때 `ArgumentException`을 던집니다.
   - 이는 입력 데이터그램의 불량에 의한 실패가 아니라 API 호출자의 사전조건(버퍼 제공 계약) 위반에 대한 것이며, 내부 연계 클래스인 `SealedDatagramIntake`는 항상 `limits.Inbound` 크기의 버퍼를 제공하여 예외가 발생하지 않도록 보장하므로 결점이 아닙니다.

3. **`SealedDatagramIntake.Offer`가 `DropReason.None`을 반환하는 정상 수신 후 거절 케이스**
   - `TryOpen`과 `FragmentHeader.TryRead`가 성공한 뒤 `ReassemblyTable.Offer`에서 예산 초과/중복 등으로 거절될 때 `out DropReason reason`이 `None`으로 남습니다.
   - 문서상 `SealedDatagramIntake.Offer`의 `out DropReason`은 봉인 해제 단계(SealRejected)의 사유를 반환하기 위한 것이며, D7 도메인 진입 후의 판정은 반환값 `FragmentAdmission` 및 내부 `CounterBank` 집계로 완결되도록 설계되었으므로 결점이 아닙니다.

4. **`PathLimits` 및 `MessageSplitter`의 스레드 비안전성**
   - `PathLimits._outbound` 필드의 가변성 및 `MessageSplitter._frameScratch` 단일 버퍼 공유는 멀티스레드 환경에서 안전하지 않습니다.
   - 엔진이 단일 스레드 이벤트 루프/폴(poll) 전제로 동작한다는 점이 `ASYMMETRY-NOTES.md` §5.3 및 `EXTENSION-NOTES.md` §5.6에 명시되어 있으므로 결점이 아닙니다.
