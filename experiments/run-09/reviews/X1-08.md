### 1. `ReassemblyDeliveryPipeline.DrainToApplication`에서 슬롯 재사용 검증 시 `ConnectionTag` 미검사로 인한 타 연결 슬롯 오배달 및 활성 슬롯 파괴
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50-52` (`src/Assembly/Triggers/ReassemblyCompletionTrigger.cs:11`, `src/Assembly/Resources/ReassemblySlotResource.cs:27`)
- **무엇이 어긋나는가**:
  `ReassemblyId`는 전역 고유 번호가 아니라 연결별 식별자(`(ConnectionTag, ReassemblyId)`)로 정의되어 있으며(`DEVIATIONS.md` 계획이 답을 주지 못한 지점 3), `DeferredReassemblyDeliveryRecord`에도 `ConnectionTag`가 저장됩니다.
  그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 큐에서 꺼낸 작업(`work`)의 `SlotIndex`를 검증할 때 `slot.ReassemblyId != work.ReassemblyId`만 검사하고, `slot.ConnectionTag == work.ConnectionTag`는 검사하지 않습니다.
  만약 연결 A의 메시지가 완성되어 전달 대기 큐에 등록된 후 연결 A가 회수(`ReclaimConnection`)되어 슬롯이 반납되고, 동일한 슬롯 인덱스가 동일한 `ReassemblyId`를 사용하는 연결 B에 재할당되어 완성된 경우, `DrainToApplication`은 슬롯의 `ConnectionTag`가 연결 B로 바뀌었음에도 이를 감지하지 못하고 연결 B의 슬롯을 연결 A의 작업으로 간주하여 처리한 뒤 슬롯을 해제(`_arena.Release(slot)`, `_pool.Return(lease)`)합니다. 이로 인해 연결 B의 활성 슬롯이 조기 파괴되고, 연결 B의 정상 배달 큐 항목은 나중에 슬롯이 닫힌 것으로 인식되어 건너뛰어집니다.
- **재현 방법**:
  1. 연결 A(`0xA1`)에서 `ReassemblyId = 1`인 메시지를 전송하여 완성시킴 (`FileDelivery`로 큐에 `SlotIndex=0, ConnectionTag=0xA1, ReassemblyId=1` 적립).
  2. `Poll`을 돌려 배달하기 전에 연결 A를 회수(`world.Reclamation.ReclaimConnection(0xA1)`)하여 슬롯 0을 반납.
  3. 연결 B(`0xB2`)에서 `ReassemblyId = 1`인 메시지를 전송하여 슬롯 0을 재할당받고 완성시킴.
  4. `world.Delivery.DrainToApplication(sink)` 호출.
  5. `DrainToApplication`이 슬롯 0의 현재 `ConnectionTag`(`0xB2`)와 작업의 `ConnectionTag`(`0xA1`)가 불일치함에도 `ReassemblyId == 1`만 보고 통과시켜 슬롯 0을 해제함. 이후 연결 B의 배달 항목은 이미 해제된 슬롯으로 인식되어 영구 누락됨.
- **확신도**: 확신

### 2. `ReassemblyExpirySweepPipeline.SweepExpired`가 배달 대기 중인 완성된 메시지를 마감 만료로 오판하여 폐기 및 유실
- **유형**: 자기모순 / 자원 누수
- **어디**: `src/Assembly/Pipelines/ReassemblyExpirySweepPipeline.cs:46-60` 및 `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:50`, `harness/Program.cs:1648-1652`
- **무엇이 어긋나는가**:
  문서(`DEVIATIONS.md` 이탈 5, `ReassemblyExpirySweepPipeline.cs:9`)는 마감 만료 회수를 "미완성으로 남겨진 것(what is left unfinished)"을 회수하는 메커니즘으로 정의하고 있으며, 완성된 메시지는 `ReassemblyCompletionTrigger`가 전달 흐름을 적립하고 애플리케이션 호출이 반환된 후 안전하게 반납하도록 규정하고 있습니다.
  그러나 `ReassemblySlotResource`에는 `Completed` 상태가 별도로 존재하지 않아 완성 후에도 `State == Open`을 유지합니다. `ReassemblyExpirySweepPipeline.SweepExpired`는 슬롯이 이미 완성되었는지(`ReassemblyCompletionFragment.Evaluate(slot.ArrivalBitmap, slot.FragmentCount).IsComplete`)를 확인하지 않고 오직 `slot.DeadlineTick`만 보고 슬롯을 해제하며 `DropReason.ReassemblyDeadlineExpired`로 집계합니다.
  게다가 `AssemblyWorld.Poll`의 실행 순서가 `Sweep.SweepExpired()` -> `Delivery.DrainToApplication()`이므로, 메시지가 완전히 조립된 시점으로부터 마감 시간(20,000ms)이 지난 시점에 `Poll`이 호출되면, `SweepExpired`가 완성된 메시지 슬롯을 만료로 간주하여 강제 회수하고, 직후 실행된 `DrainToApplication`은 슬롯이 `Free`로 바뀐 것을 보고 배달을 건너뛰어 완성된 메시지가 애플리케이션에 전달되지 못하고 유실됩니다.
- **재현 방법**:
  1. tick 1,000에서 메시지의 모든 조각을 정상 수신하여 완성시킴 (`FileDelivery`로 큐에 배달 작업 적립).
  2. 중간에 `Poll`을 호출하지 않고, tick 21,000 (`1,000 + ReassemblyDeadlineMilliseconds`)에 `world.Poll(21_000)` 호출.
  3. `SweepExpired()`가 `Delivery.DrainToApplication()`보다 먼저 실행되어 슬롯을 회수하고 `Counters.Read(DropReason.ReassemblyDeadlineExpired)`를 1 증가시킴.
  4. 뒤이어 실행된 `DrainToApplication()`은 `slot.State != ReassemblySlotState.Open`을 만나 배달을 중단함 (`world.Sink.Deliveries.Count == 0`).
  5. 모든 조각이 정상 수신 완료되었던 메시지가 애플리케이션에 전달되지 않고 소실됨.
- **확신도**: 확신

### 3. 상수 관계 X7에서 순번 공간 고갈 방지 검증식의 연산 방향 및 차원 오류
- **유형**: 계산 오류
- **어디**: `src/Stubs/EngineConstantsRecord.cs:359-360`
- **무엇이 어긋나는가**:
  관계 X7(357-360행)의 목적은 "한 시대에서 허용하는 최대 바이트 수(`EpochByteLimit`)가 64비트 순번 공간(`2^64`)보다 훨씬 먼저 시대를 전환시키므로 `SealKeyScheduleExhausted`가 산술적으로 도달 불가능함"을 검증하는 것입니다.
  한 시대에 전송 가능한 최대 데이터그램(순번) 수는 `EpochByteLimit / MinSealedDatagramBytes` (16,777,216 / 53 ≈ 316,551)이므로, 이 값이 순번 공간(`long.MaxValue` 또는 `ulong.MaxValue`) 이상인지를 검사해야 합니다 (`EpochByteLimit / MinSealedDatagramBytes >= long.MaxValue`).
  그러나 359행은 `if (EpochByteLimit >= long.MaxValue / MinSealedDatagramBytes)`로 작성되었습니다.
  `long.MaxValue / MinSealedDatagramBytes`는 `9,223,372,036,854,775,807 / 53 ≈ 1.74 × 10^17`이며, 바이트 단위인 `EpochByteLimit`(16,777,216 B)과 무의미한 차원의 거대 상수를 직접 비교하고 있어 관계식의 계산 및 차원 단위가 완전히 틀렸습니다.
- **재현 방법**:
  `EngineConstantsRecord.cs` 359행의 관계식을 확인:
  `EpochByteLimit` (16,777,216)과 `long.MaxValue / 53` (174,025,887,487,825,958)을 직접 비교합니다.
  `EpochByteLimit`이 명세 허용 범위(2^20 ~ 2^32) 내의 어떤 값으로 설정되더라도 우변이 1.74 × 10^17이므로 이 조건식은 순번 공간 고갈 가능성을 전혀 판별하지 못합니다.
- **확신도**: 확신

### 5. `DatagramOpenPipeline.cs` 내 도달 불가능한 죽은 코드 분기
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:95` 및 `src/Security/Pipelines/DatagramOpenPipeline.cs:135`
- **무엇이 어긋나는가**:
  1. 95행: `if (!SealedDatagramHeaderRecord.TryParse(datagram, out var header))`
     68행에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes` (53 B)를 통해 이미 길이를 검사했으므로, 93행 도달 시 `datagram.Length >= 53`입니다. `SealedDatagramHeaderRecord.WireBytes`는 24 B이므로 `TryParse`는 항상 `true`를 반환하며 95행의 반환문은 도달할 수 없습니다.
  2. 135행: `if (slot == EpochSlotCode.Next) key.Dispose();`
     128행에서 `slot == EpochSlotCode.Next`인 경우 `window`는 `ReplayWindowRecord.Empty`로 설정됩니다. `ReplayWindowRecord.Empty`는 `HasAccepted == false`이므로 `ReplayWindowFragment.Evaluate(header.Sequence, window)`는 37행에 의해 무조건 `ReplaySequenceVerdict.Fresh`를 반환합니다. 따라서 133행의 `replayVerdict != ReplaySequenceVerdict.Fresh` 조건문 내부의 135행 분기(`slot == EpochSlotCode.Next`)는 산술적으로 도달 불가능합니다.
- **재현 방법**:
  135행: 다음 시대를 지목하는 임의의 합법/불법 데이터그램을 구성하여 `OpenDatagram`에 전달하더라도 `ReplayWindowFragment.Evaluate`는 항상 `Fresh`를 반환하므로 135행의 `key.Dispose()`는 실행되지 않습니다.
  95행: 68행을 통과한 모든 데이터그램은 길이가 최소 53 B 이상이므로 `TryParse` 실패 분기(95행)에 진입하지 않습니다.
- **확신도**: 확신

### 6. `FragmentOffsetBoundsFragment.cs` 내 수학적으로 도달 불가능한 오프셋 초과 검사 분기
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  `FragmentOffsetBoundsFragment.Evaluate`의 54행 `if (offset + expected > total)`은 항상 `false`입니다.
  앞선 43행 `if (offset >= total)`을 통과했으므로 `offset < total`이 보장되며, `expected = header.ExpectedPayloadLengthBytes`는 `min(total - offset, uniform)`으로 계산되므로 정의상 `expected <= total - offset`입니다.
  따라서 `offset + expected <= total`이 수학적으로 항상 성립하므로, 54~57행의 `Verdict<FragmentPlacementRecord>.Reject(DropReason.FragmentOffsetOutOfBounds)` 분기는 절대 실행될 수 없는 죽은 코드입니다.
- **재현 방법**:
  임의의 `FragmentationHeaderRecord`를 구성하여 43행을 통과시키면, `ExpectedPayloadLengthBytes`의 정의에 의해 `offset + expected <= total`이 항상 성립하므로 56행의 거부 반환문에 도달할 수 없습니다.
- **확신도**: 확신
