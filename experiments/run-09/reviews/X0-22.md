## 결점

### 1. EngineOptions.Validate의 건수 축 정합성 예외 메시지 모순
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/Stubs/EngineOptions.cs:256-259`
- **무엇이 어긋나는가**: 
  `EngineOptions.Validate()`는 `PerConnectionReassemblyContexts <= PerConnectionReassemblyBytes / ContextOverheadBytes` 불변식을 검사하면서, 실패 시 메시지로 `"N_conn(...) > ⌊B_conn/A_ctx⌋(...) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."`를 출력합니다.
  그러나 이 부등식의 실제 수학적·의미적 목적은 최소 부기 비용($A_{ctx}$)만으로 연결별 건수($N_{conn}$)를 가득 채웠을 때의 최소 예약 바이트($N_{conn} \times A_{ctx}$)가 연결별 바이트 상한($B_{conn}$)을 초과하지 않도록 보장하는 것입니다.
  실제 런타임에서 작은 페이로드 메시지들이 들어올 경우, 바이트 축이 소진되기 전에 건수 축($N_{conn}$)에 먼저 도달하여 거절되는 것은 의도된 정상 동작이며(하네스 검사 6-(b) `Check06_PerConnectionCap`에서 이를 명시적으로 검증함), "건수 축이 바이트 축보다 먼저 걸릴 수 없다"는 설명은 코드의 의도 및 실제 동작과 정반대로 진술되어 있습니다.
- **재현 방법**:
  `new EngineOptions { PerConnectionReassemblyContexts = 2049, PerConnectionReassemblyBytes = 262144, ContextOverheadBytes = 128 }.Validate()`를 호출하면 `ArgumentException`이 발생하며 `"설정 오류 [PerConnectionReassemblyContexts]: N_conn(2049) > ⌊B_conn/A_ctx⌋(2048) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다."` 메시지가 출력됩니다.
- **확신도**: 확신

### 2. MessageSplitter.WriteFragment의 TryWrite 실패 시 예외 매개변수명 불일치
- **유형**: 자기모순
- **어디**: `src/Realtime.Assembly/MessageAssembly/MessageSplitter.cs:186-187`
- **무엇이 어긋나는가**:
  `MessageSplitter.WriteFragment`는 조각 프레임 머리말을 내부 스크래치 버퍼 `frame`에 기록할 때 `header.TryWrite(frame)`의 실패를 검사합니다. 이때 실패 시 던지는 예외가 `new ArgumentException("머리말을 쓸 공간이 없다.", nameof(datagramDestination))`로 작성되어 있습니다.
  실패한 대상은 내부 스크래치 버퍼 `frame`이며, `datagramDestination` 버퍼의 크기 검증은 이미 174~175행에서 완료되었습니다. 따라서 호출자에게 전달되는 예외의 매개변수 이름이 실제 검사 대상과 불일치합니다.
- **재현 방법**:
  `MessageSplitter.WriteFragment` 실행 중 `_frameScratch` 공간 부족으로 `header.TryWrite(frame)`이 `false`를 반환하는 상황(또는 정적 코드 분석)에서 발생하는 `ArgumentException.ParamName`이 `"datagramDestination"`으로 반환됨을 확인합니다.
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`PathLimits.LowerOutbound`에서 `RequireRelationsFor` 미호출 (`src/Realtime.Assembly/Stubs/PathLimits.cs:126-136`)**
   - `PathLimits` 생성 시 `[D_floor, D_max]` 범위 및 방향별 관계($K4, K5, K9$)가 이미 검증되었고, `LowerOutbound`는 `D_floor` 이상으로만 낮출 수 있습니다. $P = L - H$에서 $L \ge D_{floor}$이면 $P \ge P_{floor}$가 보장되고, $\lceil M/P \rceil$는 $L$에 대해 단조 감소하므로 허용 범위 내에서 상한을 낮추어도 $F \le 64$ 불변식이 항상 유지되므로 중복 검사 생략은 정상입니다.

2. **`ReplayWindow`가 `struct`로 정의되어 `EpochState`에 포함된 점 (`src/Realtime.Assembly/DatagramSecurity/ReplayWindow.cs`, `DatagramOpener.cs`)**
   - `ReplayWindow`는 값 타입 구조체이지만, `DatagramOpener` 내부의 `EpochState` 힙 객체(class)의 필드로 저장되어 있습니다. `DatagramOpener.TryOpen`에서 `state.Window.Accept(...)` 호출 시 힙 상의 인스턴스 필드가 제자리에서 직접 수정되므로 값 복사로 인한 상태 유실이 발생하지 않습니다.

3. **`ReassemblyTable.Offer`의 `FreeSlot() < 0` 도달 불가능 분기 (`src/Realtime.Assembly/MessageAssembly/ReassemblyTable.cs:118-126`)**
   - `_budget.TryReserve`에서 이미 건수 축 상한(`ContextLimit == _slots.Length`)을 검사하므로 정상적인 제어 흐름에서는 `FreeSlot() < 0`에 도달하지 않습니다. 이는 방어적 프로그래밍 목적으로 자원을 정리하고 거절하도록 구현된 안전 장치입니다.

4. **`ASYMMETRY-NOTES.md` §5 및 `EXTENSION-NOTES.md` §5에 기술된 남은 제약사항들**
   - 단일 스레드 폴 전제, 2^32 시대 되감기, 들어오는 쪽 최악치의 허용 범위 하한 기준 산출 등은 설계 명세 범위 밖의 제약과 트레이드오프에 대한 근거가 문서에 명확히 기록되어 있으며, 현재 요구사항 내에서 일관되게 동작하므로 결점으로 판정하지 않았습니다.
