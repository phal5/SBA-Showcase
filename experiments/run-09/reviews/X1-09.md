### 1. `FragmentDuplicateFragment.Evaluate`의 64비트 시프트 오버플로로 인한 인덱스 64 오판정
- **유형**: 미강제 불변식 / 계산 오류
- **어디**: `src/Assembly/Fragments/FragmentDuplicateFragment.cs:26-27`
- **무엇이 어긋나는가**: 
  - `FragmentDuplicateFragment`는 `(index, arrival bitmap) → new fragment / duplicate` 판정을 내리는 순수 함수로 정의되어 있습니다.
  - C# 및 .NET 런타임에서 64비트 `ulong`에 대한 비트 시프트 연산(`1UL << fragmentIndex`)은 우측 피연산자에 대해 하위 6비트 마스킹(`fragmentIndex & 0x3F`)을 수행합니다. 따라서 `fragmentIndex = 64`가 입력될 경우 `1UL << 64`는 `1UL << 0` (1UL, 0번 비트)로 평가됩니다.
  - 반면 동일한 64 경계를 다루는 `ReassemblyCompletionFragment.cs:15`에서는 `fragmentCount >= 64 ? ulong.MaxValue : (1UL << fragmentCount) - 1UL;`와 같이 명시적으로 64 경계를 방어하고 있습니다.
  - `FragmentDuplicateFragment`는 `fragmentIndex`의 범위를 검증하거나 64 이상의 값을 방어하지 않으므로, 0번 조각이 수신되어 0번 비트가 세워진 비트맵에 대해 `fragmentIndex = 64`로 호출하면 64번 조각이 중복 수신된 것으로 잘못 판정합니다.
- **재현 방법**:
  `FragmentDuplicateFragment.Evaluate(64, 1UL)`을 호출합니다.
  - 기대 결과: 64번 조각은 비트맵에 존재하지 않으므로 `FragmentArrivalVerdict.NewFragment`를 반환하거나 불변식 위반으로 처리되어야 함.
  - 실제 결과: `1UL << 64`가 `1UL`로 계산되어 `(1UL & 1UL) != 0`이 참이 되며 `FragmentArrivalVerdict.DuplicateFragment`가 반환됨.
- **확신도**: 확신

### 2. `DatagramOpenPipeline.OpenDatagram` 2단계 파싱의 도달 불가능한 갈래 (죽은 코드)
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:68-72` 및 `src/Security/Pipelines/DatagramOpenPipeline.cs:94-97`
- **무엇이 어긋나는가**:
  - `DatagramOpenPipeline.cs` 68~72행(1단계)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes` (53바이트)인 경우 `SealedDatagramLengthOutOfRange`로 즉시 반환(거절)합니다.
  - 94~97행(2단계)에서 `SealedDatagramHeaderRecord.TryParse(datagram, out var header)`를 호출하여 파싱 실패 시 `SealedDatagramLengthOutOfRange`를 반환하도록 분기하고 있습니다.
  - 그러나 `SealedDatagramHeaderRecord.TryParse`가 `false`를 반환하는 유일한 조건은 `source.Length < WireBytes` (24바이트)입니다.
  - 1단계에서 이미 길이가 53바이트 이상임이 보장되므로 `TryParse`는 항상 `true`를 반환하며, 94~97행의 `if (!TryParse)` 분기 및 거절 코드는 절대 실행될 수 없는 도달 불가능한 죽은 코드입니다.
- **재현 방법**:
  `DatagramOpenPipeline.OpenDatagram`에 어떤 바이트 배열 입력을 전달하더라도 96행의 `return Refuse(DropReason.SealedDatagramLengthOutOfRange, ...)`에는 도달할 수 없습니다. 53바이트 미만은 71행에서 걸러지고, 53바이트 이상은 `TryParse`가 항상 성공합니다.
- **확신도**: 확신

### 4. 연결 해제 시 보안 연관 및 경로 상한 표 자원의 미회수 (회수 파이프라인 누락)
- **유형**: 자원 누수
- **어디**:
  - `src/Assembly/Pipelines/ConnectionReassemblyReclamationPipeline.cs:37-57`
  - `src/Security/Resources/SecurityAssociationTableResource.cs:73-77`
  - `src/Path/Resources/PathLimitTableResource.cs:39`
- **무엇이 어긋나는가**:
  - R8.5 및 설계 원칙에 따르면 연결 종료 시 해당 연결이 점유하던 모든 자원이 회수되어야 합니다.
  - `SecurityAssociationTableResource.ReclaimConnection` 및 `PathLimitTableResource.ReclaimConnection`이 구현되어 있으나, 연결 해제를 총괄하는 `ConnectionReassemblyReclamationPipeline`이나 하네스의 기본 연결 종료 흐름에는 이들이 결합되어 있지 않습니다.
  - 결과적으로 연결이 닫힐 때 재조립 슬롯과 버퍼는 회수되지만, `SecurityAssociationTableResource`의 `_send`, `_receive` 딕셔너리 및 `PathLimitTableResource`의 `_byConnection` 딕셔너리 항목은 연결이 닫혀도 명시적으로 별도 호출하지 않는 한 해제되지 않고 영구 잔류합니다.

  2. `ConnectionReassemblyReclamationPipeline.ReclaimConnection(0x999)`를 호출하여 연결을 정리합니다.
  3. `SecurityAssociationTableResource.SendAssociationCount` 또는 `PathLimitTableResource.IsStated(0x999)`를 확인합니다.
  4. 기대 결과: 연결 종료로 모든 상태가 제거되어야 함.
  5. 실제 결과: `_send`/`_receive` 키와 `_byConnection`에 해당 태그의 항목이 그대로 남아 있습니다.

## 결점이 아니라고 판단한 것

1. **산술적으로 도달 불가능한 거절 사유 5종 (`ReassemblyPerConnectionFragmentBudgetExhausted`, `ReassemblyPerConnectionByteBudgetExhausted`, `ReassemblyTotalFragmentBudgetExhausted`, `ReassemblyTotalByteBudgetExhausted`, `SealKeyScheduleExhausted`)**:
   - `ReassemblyAdmissionFragment` 및 `SealedDatagramSendPipeline`에 정의된 이들 분기는 상수 관계식(K1, K2, §7.4-3, X7)에 의해 슬롯 축 및 16 MiB 에포크 상한이 먼저 도달하므로 현재 상수 구성 하에서는 도달할 수 없습니다.
   - 그러나 이는 스펙 변경 S2("계수하지 않는 축은 무한하다") 원칙에 따라 상수가 변경될 때 즉시 활성화될 수 있도록 방어적으로 배치된 것이며, `DEVIATIONS.md` 및 `EXTENSION-NOTES.md`에 도달 불가능함이 명시되어 있고 하네스 검사 7번에서 계수가 0임을 회귀 검증하고 있으므로 결함이 아닌 의도된 설계 불변식으로 판단했습니다.

2. **`EngineConstantsRecord.FindViolatedConstantRelation`의 CS0162 경고 억제 및 상수 비교 분기**:
   - 상수 비교식으로 인해 컴파일 시점에 dead branch로 판정되지만, 런타임 시작 시 정적 단언(assert) 역할을 수행하고 문서화 역할을 겸하도록 의도된 구성(`pragma warning disable CS0162`)이므로 결함이 아닙니다.

3. **`AesGcm.Decrypt` 실패 시 예외 발생으로 인한 힙 할당 (E10 단방향 제약)**:
   - 위조 데이터그램 수신 시 .NET의 `AesGcm` API 특성상 `CryptographicException`이 발생하여 예외 객체 할당이 일어납니다. 이는 `EXTENSION-NOTES.md §5.6`에 명시되어 있듯이 정상 경로(steady path)에 대해서만 제로 할당(E10)을 만족하도록 규정되어 있으므로 결함이 아닙니다.
