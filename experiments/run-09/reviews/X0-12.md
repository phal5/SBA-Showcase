### 1. `DropReason.cs`의 `MalformedDatagram` 요약 주석과 실제 처리/분리 사유의 자기모순
- **유형**: 자기모순 / 중복 불일치
- **어디**:
  - `src/Realtime.Assembly/Stubs/DropReason.cs:39`
  - `src/Realtime.Assembly/Stubs/DropReason.cs:63-69`
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:121-125`
- **무엇이 어긋나는가**:
  - `DropReason.cs:39`의 `MalformedDatagram` XML 요약 주석에는 `봉인된 데이터그램의 바이트 배치가 어긋난다(너무 짧거나 경로 상한을 넘는다).`라고 적혀 있어 경로 상한을 넘는 경우에도 `MalformedDatagram`이 발생한다고 명시하고 있습니다.
  - 그러나 방향별 상한 확장(D5) 이후, `DatagramOpener.cs:121-125`에서는 들어오는 쪽 상한을 넘는 데이터그램에 대해 `DropReason.InboundDatagramTooLarge`를 반환하도록 사유를 분리하였습니다. 또한 `DropReason.cs:63-69` 주석 및 `ASYMMETRY-NOTES.md` §2에서도 이탈 #3 규칙에 따라 운영자 조치가 갈리므로 `MalformedDatagram`("배치가 깨진 바이트")과 `InboundDatagramTooLarge`("피어가 알린 상한을 지키지 않음")를 분리했음을 명확히 밝히고 있습니다. 하네스 검사 18(`harness/Program.cs:1562`)에서도 상한 초과 데이터그램 수신 시 `MalformedDatagram`이 0건이어야 함을 단언(`if (rig.Counters[DropReason.MalformedDatagram] != 0) return "상한 초과가 MalformedDatagram으로 뭉뚱그려졌다";`)합니다.
  - 따라서 `DropReason.cs:39`의 주석은 변경 전의 기술이 그대로 남아 있어 실제 코드 구현 및 동일 파일 내의 다른 주석(63-69행)과 모순됩니다.
- **재현 방법**:
  1. `PathLimits(options, 1452, 1200)`인 연결을 생성합니다(들어오는 쪽 상한 1,200 B).
  2. 1,201 B 크기로 정상 봉인된 데이터그램을 `DatagramOpener.TryOpen` 또는 `SealedDatagramIntake.Offer`에 입력으로 전달합니다.
  3. 반환된 사유를 확인하면 `DropReason.InboundDatagramTooLarge` (15)가 반환되고, `_counters[DropReason.MalformedDatagram]`은 0을 유지합니다. 주석(39행)이 설명하는 `MalformedDatagram`은 발생하지 않습니다.
- **확신도**: 확신

### 2. `Realtime.Assembly.csproj` 프로젝트 주석과 실제 어셈블리 포함 모듈 간의 모순
- **유형**: 자기모순
- **어디**:

  - `src/Realtime.Assembly/DatagramSecurity/DatagramSealer.cs:1-155`
  - `src/Realtime.Assembly/DatagramSecurity/DatagramOpener.cs:1-236`
- **무엇이 어긋나는가**:
  - `Realtime.Assembly.csproj:4` 주석은 `D7 메시지 조립만. 소켓·암호·핸드셰이크·채널은 이 어셈블리에 없다.`라고 명시하고 있습니다.
  - 그러나 보안 확장(E1~E10) 구현에 따라, AES-256-GCM 암복호화 및 HKDF-SHA256 키 유도를 담당하는 `DatagramSecurity` 모듈(`DatagramSealer`, `DatagramOpener`, `SessionKeys` 등)이 해당 어셈블리 프로젝트(`src/Realtime.Assembly/`) 내에 직접 구현되어 포함되었습니다.
  - 즉, 어셈블리 내에 암호화/복호화 엔진이 직접 포함되어 있음에도 불구하고 프로젝트 파일 주석에는 "암호는 이 어셈블리에 없다"고 기술되어 모순됩니다.
- **재현 방법**:
  1. `src/Realtime.Assembly/Realtime.Assembly.csproj`를 컴파일합니다.
  2. 생성된 `Realtime.Assembly.dll`을 리플렉션 또는 `ildasm` 등으로 검사하면 `System.Security.Cryptography.AesGcm`을 직접 사용하는 `Realtime.Assembly.DatagramSecurity.DatagramSealer` 및 `DatagramOpener` 타입이 해당 어셈블리에 포함되어 있음을 확인할 수 있습니다.
- **확신도**: 확신

### 3. `EngineOptions.Validate()`의 `N_conn` 검증 실패 메시지의 논리 설명 모순
- **유형**: 자기모순
- **어디**:
  - `src/Realtime.Assembly/Stubs/EngineOptions.cs:256-259`
  - `harness/Program.cs:617-618`
- **무엇이 어긋나는가**:
  - `EngineOptions.cs:256-259`에서 `Require(PerConnectionReassemblyContexts <= PerConnectionReassemblyBytes / ContextOverheadBytes, nameof(PerConnectionReassemblyContexts), $"N_conn({PerConnectionReassemblyContexts}) > ⌊B_conn/A_ctx⌋({PerConnectionReassemblyBytes / ContextOverheadBytes}) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다.");`로 검증 실패 메시지를 출력합니다.
  - 그러나 이 검사의 실제 목적(254행 주석 `// 건수 축이 바이트 축을 무의미하게 만들지 않을 것 (R10.4 / 계획 K12)`)은 `N_conn > B_conn / A_ctx`가 되면 최소 부기(A_ctx)만으로도 바이트 축이 먼저 소진되어 건수 상한(`N_conn`)에 물리적으로 도달할 수 없게 되는 현상을 막는 것입니다.
  - 작은 메시지가 다수 도착하는 상황에서는 건수 축(`N_conn`)이 바이트 축(`B_conn`)보다 먼저 걸리는 것이 정상적인 설계 동작이며, 하네스 검사 6(b)(`harness/Program.cs:617-618`)에서도 작은 메시지 도착 시 건수 축이 먼저 걸리는지(`if (t2.Budget.Bytes >= o.PerConnectionReassemblyBytes) return "건수 축이 아니라 바이트 축이 먼저 걸렸다";`)를 확인하고 있습니다.
  - 따라서 예외 메시지의 "건수 축이 바이트 축보다 먼저 걸릴 수 없다"는 서술은 실제 설계 의도 및 검증하려는 바와 정반대로 적혀 있습니다.
- **재현 방법**:
  1. `EngineOptions`에서 `PerConnectionReassemblyBytes = 262_144`, `ContextOverheadBytes = 128`인 상태에서 `PerConnectionReassemblyContexts = 2049`로 설정하고 `options.Validate()`를 호출합니다.
  2. 실제 발생 결과: `ArgumentException`이 발생하며 메시지로 `설정 오류 [PerConnectionReassemblyContexts]: N_conn(2049) > ⌊B_conn/A_ctx⌋(2048) — 건수 축이 바이트 축보다 먼저 걸릴 수 없다.`가 출력됩니다. (실제로는 바이트 축이 항상 먼저 소진되어 N_conn이 무의미해지는 상황임에도 건수 축이 먼저 걸릴 수 없다고 반대로 기술함).
- **확신도**: 확신

## 결점이 아니라고 판단한 것

1. **`MaxFragmentsPerMessage (F = 64)`가 도달 불가능한 여유(최대 58조각)인 점**
   - 하한 경로(`D_floor - H = 1,142 B`) 기준 65,536 B 메시지는 최대 58조각으로만 분할될 수 있어 59~64는 유효한 입력으로 도달할 수 없습니다.
   - 이는 `DEVIATIONS.md` ("계획이 틀렸던 지점 (1)") 및 하네스 검사 2에서 계획 수립 당시의 계산 착오였음을 명확히 기록하고 의도적으로 고정해 둔 역사적/설계적 결정이므로 결점이 아닙니다.

2. **`MessageSplitter`의 `_frameScratch` 단일 버퍼 공유**
   - 분할기 인스턴스가 단일 스레드 폴(poll) 환경에서 사용된다는 전제가 `EXTENSION-NOTES.md` §5-6 및 `ASYMMETRY-NOTES.md` §5-3에 명시되어 있으므로 결점이 아닙니다.

3. **`DatagramOpener.TryOpen`의 `Promote` 및 상태 변경 시점**
   - AEAD 복호화 검증이 완료된 후에만 `Promote` 및 `Window.Accept`가 호출되어 인증 실패 데이터그램이 어떤 상태도 남기지 않도록 하는 E4 요구사항을 정확히 준수하고 있습니다.

4. **`CounterBank.Total`에서 인덱스 0(`DropReason.None`)을 건너뛰는 점**
   - `DropReason.None`은 폐기(Drop)가 발생하지 않은 정상이므로 총 폐기 횟수 합산에서 제외하는 것이 올바른 동작입니다.

5. **`UIntExtensions.AsInt`의 checked 변환**
   - `header.TotalLength`는 호출 전에 `FragmentValidator.Validate`에서 `MaxMessageBytes (65,536)` 이하임이 검증된 상태에서만 사용되므로 정수 오버플로가 발생하지 않습니다.
