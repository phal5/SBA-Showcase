## 결점

### 1. `ReassemblyDeliveryPipeline`에서 슬롯 재사용 검증 시 `ConnectionTag` 불일치를 검사하지 않음
- **유형**: 미강제 불변식
- **어디**: `src/Assembly/Pipelines/ReassemblyDeliveryPipeline.cs:49-52` 및 `DEVIATIONS.md:39-43`
- **무엇이 어긋나는가**:
  - `DEVIATIONS.md` 39~43행 및 `ReassemblyArenaResource.cs`는 `ReassemblyId`가 전역 고유값이 아니라 **연결별(per-connection)** 식별자임을 명시하고 있습니다(색인 키: `(ConnectionTag, ReassemblyId)`).
  - 지연 작업 큐에 등록되는 `DeferredReassemblyDeliveryRecord`는 `SlotIndex`, `ConnectionTag`, `ReassemblyId`를 모두 보관합니다.
  - 그러나 `ReassemblyDeliveryPipeline.DrainToApplication`은 큐에서 꺼낸 작업을 처리할 때 슬롯의 상태(`slot.State != ReassemblySlotState.Open`)와 `slot.ReassemblyId != work.ReassemblyId`만 검사하고, **`slot.ConnectionTag != work.ConnectionTag` 검사를 누락**했습니다.
  - 이로 인해 특정 슬롯이 회수된 후 동일한 `ReassemblyId`를 사용하는 다른 연결의 슬롯으로 재할당된 경우, 이전 연결의 배달 작업이 새 연결의 슬롯을 이전 연결의 배달로 오인하여 잘못 배달하고 해당 슬롯과 버퍼를 조기 반납(Release/Return)해 버리는 심각한 상태 오염이 발생합니다.
- **재현 방법**:
  1. 연결 A(`ConnectionTag = 0xAA`)로 `ReassemblyId = 1`인 메시지의 모든 조각을 전송하여 슬롯(예: `SlotIndex = 0`)에서 완성을 발생시킵니다. (`DeferredWork`에 `(SlotIndex: 0, ConnectionTag: 0xAA, ReassemblyId: 1)` 적립)
  2. `DrainToApplication`이 호출되기 전에 `Reclamation.ReclaimConnection(0xAA)`을 호출하여 연결 A를 회수합니다. 슬롯 0이 반납되어 자유 목록으로 돌아갑니다.
  3. 연결 B(`ConnectionTag = 0xBB`)로 `ReassemblyId = 1`인 메시지의 조각들을 전송하여 슬롯 0을 새로 열고 완성시킵니다.
  4. `DrainToApplication`을 실행하면, 큐에 남아 있던 연결 A의 작업 항목이 슬롯 0(`ConnectionTag = 0xBB`, `ReassemblyId = 1`)을 검사할 때 `ReassemblyId`가 1로 일치하므로 연결 B의 완성 메시지를 연결 A의 작업으로 처리하여 배달하고 슬롯 0을 조기 반납해 버립니다.
- **확신도**: 확신

### 2. `FragmentOffsetBoundsFragment` 내 `offset + expected > total` 조건문 도달 불가능 (항상 거짓)
- **유형**: 죽은 코드
- **어디**: `src/Assembly/Fragments/FragmentOffsetBoundsFragment.cs:54-57`
- **무엇이 어긋나는가**:
  - `FragmentationHeaderRecord.ExpectedPayloadLengthBytes`는 다음과 같이 계산됩니다:
    ```csharp
    int remaining = (int)TotalLengthBytes - offset;
    return remaining < uniform ? remaining : uniform;
    ```
  - `FragmentOffsetBoundsFragment.Evaluate`의 43행에서 `offset >= total`인 경우 이미 거절되므로, 54행에 도달했을 때 `offset < total` (즉, `remaining = total - offset > 0`)이 보장됩니다.
  - `expected`는 항상 `remaining` 이하의 값(`remaining < uniform ? remaining : uniform`)을 가지므로, `offset + expected`는 수학적으로 항상 `offset + (total - offset) = total` 이하입니다.
  - 따라서 54행의 `if (offset + expected > total)` 조건은 어떠한 입력에서도 항상 `false`이며, 56행의 `FragmentOffsetOutOfBounds` 거절 코드는 절대로 실행될 수 없는 죽은 코드입니다.
- **재현 방법**:
  - `FragmentationHeaderRecord`에 어떠한 유효/기형 값을 주더라도, 43행(`offset >= total`)과 49행(`arrivedPayloadLengthBytes != expected`)을 통과한 상태에서는 `offset + expected <= total`이 항상 성립하므로 56행 분기를 실행시킬 수 없습니다.
- **확신도**: 확신

### 3. `DatagramOpenPipeline` 2단계의 헤더 파싱 실패 검사 도달 불가능 (항상 참/거짓)
- **유형**: 죽은 코드
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:94-96`
- **무엇이 어긋나는가**:
  - `DatagramOpenPipeline.OpenDatagram` 1단계(68~72행)에서 `datagram.Length < EngineConstantsRecord.MinSealedDatagramBytes` (53 B)인 경우 이미 거절되어 반환됩니다.
  - `SealedDatagramHeaderRecord.TryParse`는 입력 길이가 `WireBytes` (24 B) 미만일 때만 `false`를 반환합니다.
  - 1단계를 통과한 데이터그램은 길이가 최소 53 B 이상이므로, 94행의 `SealedDatagramHeaderRecord.TryParse(datagram, out var header)`는 항상 `true`를 반환합니다.
  - 따라서 94행의 `if (!SealedDatagramHeaderRecord.TryParse(...))` 조건은 항상 `false`이며, 96행의 거절 코드는 결코 실행되지 않는 죽은 코드입니다.
- **재현 방법**:
  - 68행의 최소 길이 검사를 통과한 모든 데이터그램에 대해 94행의 `TryParse`는 항상 `true`를 반환하므로, 96행의 `Refuse` 분기를 실행시키는 입력은 존재하지 않습니다.

### 4. `DatagramOpenPipeline` 주석에서 `MaxSealedDatagramBytes`를 평문 버퍼 폭으로 잘못 설명
- **유형**: 자기모순
- **어디**: `src/Security/Pipelines/DatagramOpenPipeline.cs:64-65` 및 `src/Stubs/EngineConstantsRecord.cs:137-146`
- **무엇이 어긋나는가**:
  - `DatagramOpenPipeline.cs` 64~65행 주석에는 다음과 같이 적혀 있습니다:
    `// 1 — length. MaxSealedDatagramBytes is the width of the plaintext buffer this endpoint keeps for every connection...`
  - 그러나 `EngineConstantsRecord.cs` 137~146행에 정의된 바에 따르면:
    - 평문 스크래치 버퍼의 폭은 `MaxSealedAreaBytes` (1,374 B = 조각 헤더 12 B + 최대 조각 페이로드 1,362 B)입니다.
    - `MaxSealedDatagramBytes` (1,414 B = 봉인 덧붙이 40 B + 평문 영역 1,374 B)는 평문 버퍼 폭이 아니라 **와이어 상의 봉인된 데이터그램 최대 크기**입니다.
  - 코드 주석이 와이어 데이터그램 상한 상수를 "평문 버퍼의 폭"으로 잘못 기술하고 있어 `EngineConstantsRecord`의 정의 및 실제 버퍼 사용과 모순됩니다.
- **재현 방법**:
  - `DatagramOpenPipeline.cs:64-65` 주석 내용과 `EngineConstantsRecord.cs:137-146`의 상수 선언 및 주석을 대조하여 확인합니다.
- **확신도**: 확신
