# SBA 시공 규약 (Construction Conventions)

> `Core Concepts.md`는 SBA가 **무엇인가**를 정의합니다. 이 문서는 그것을 실제 코드베이스에
> **어떻게 강제할 것인가**를 정의합니다. 백서가 헌법이면 이 문서는 시행령입니다.
> 규약이 흔들리면 "SBA를 시험했다"는 주장 자체가 성립하지 않으므로, 여기서 정한 것은
> 예외 없이 지키고, 지킬 수 없는 지점이 나오면 **코드를 구부리는 대신 이 문서에 발견으로 기록**합니다.

---

## 0. 황금률의 기계적 검사식

백서의 황금률("한두 단어의 자연어로 완벽하게 요약 가능")은 사람의 판단에 맡기면 반드시 미끄러집니다.
이 코드베이스에서는 다음 **세 가지 기계적 조건**으로 환원합니다.

| # | 조건 | 근거 |
|---|------|------|
| G1 | 파일 하나의 요약문에 **접속사(그리고/또는/한 뒤에)가 필요하면 분할한다** | 접속사는 책임이 둘이라는 증거다 |
| G2 | 파일명 = 타입명 = 그 요약문의 명사구 | 벡터 좌표와 파일 경로가 일치해야 RAG 워프가 성립 |
| G3 | 파편은 **공개 메서드 1개**, 파이프라인은 **공개 진입점 1개** | 진입점이 둘이면 요약문도 둘이다 |

G1이 실질적 판정 기준입니다. "TCP 프레임을 읽**고** 봉인을 해제한다"는 두 파편입니다.

## 1. 블록 유형과 접미사

백서 §3의 3+2 구조에 **자원 블록 하나를 추가**했습니다. 추가 사유는 §1.1에 기록합니다.

| 블록 | 접미사 | 역할 | 순수성 | 크기 상한 |
|------|--------|------|--------|-----------|
| 인덱스 | `Index` | 런타임 진입점 겸 목차. 비즈니스 로직 0줄 | — | 선언만 |
| 파이프라인 | `Pipeline` | 유즈케이스 1개의 선형 조립 | 부수효과 허용 | 120줄 |
| 파편 | `Fragment` | 계산·검증·인코딩 공식 1개 | **순수 함수 강제** | 60줄 |
| 레코드 | `Record` | 블록 간 이동하는 불변 값 | 불변 강제 | 80줄 |
| 원장 | `Ledger` | 자가 신고 데이터의 보관함 | 적립 전용 | 80줄 |
| **자원** | `Resource` | 수명을 가진 가변 상태(소켓·풀·큐·락) | 격리된 가변 | 150줄 |

### 1.1 자원 블록을 추가한 이유 (테스트베드 발견 #1)

백서의 5블록에는 **소켓·메모리풀·수신 큐·혼잡 윈도우처럼 "수명과 가변 상태를 함께 가진 것"**의
자리가 없습니다. 파편은 순수 함수여야 하므로 소켓을 담을 수 없고, 파이프라인은 유즈케이스 1회
호출마다 태어나 죽으므로 연결이 살아 있는 동안 유지되는 상태를 담을 수 없습니다.
레코드는 불변입니다.

이 상태들을 파이프라인에 우겨넣으면 파이프라인이 곧 God-object가 되어 SBA가 무너집니다.
따라서 **자원 블록**을 도입하되, 다음 규칙으로 파편의 순수성을 보호합니다.

> **자원 블록은 공식을 담지 않는다.** 자원은 *상태를 들고 있고, 좁은 동사를 노출하고, 계산은
> 전부 파편에 위임한다.* 자원 안에서 `if`로 판단하는 순간 그 판단은 파편으로 나가야 한다.

즉 자원은 "상태의 껍데기 + 파편 호출"입니다. 이렇게 하면 이진 탐색 디버깅 시 자원 블록은
**검문소가 아니라 배선**으로 취급할 수 있고, 범인은 언제나 파편 안에 있습니다.

## 2. 파일 헤더 (RAG 좌표 앵커)

모든 `.cs` 파일은 **정확히 이 3줄**로 시작합니다. 더도 덜도 아닙니다.

```csharp
// BLOCK: <유형> · <도메인>
// DOES: <G1을 통과하는 한 문장. 접속사 없음.>
// PURE: yes | no
```

- `PURE: yes`인 파일은 정적 검사기가 필드·`static` 가변 상태·I/O 호출을 금지합니다.
- 드리프트하는 헤더(`USED-BY:` 같은 역참조)는 **의도적으로 넣지 않습니다.** 유지되지 않는
  메타데이터는 RAG를 돕는 대신 오염시킵니다. 역방향 탐색은 LSP가 이미 정확하게 합니다.

## 3. 명명 규칙

백서 §2.2의 "자연어 문장처럼 긴 이름"을 **타입과 메서드에 다르게** 적용합니다.

| 대상 | 규칙 | 예 |
|------|------|-----|
| 타입명 | 개념의 명사구 1~3단어 + 블록 접미사 | `UdpNonceFragment`, `TcpFrameHeaderRecord` |
| 공개 메서드명 | **완결된 자연어 문장** | `WriteDeterministicNonceFromEpochAndSequence` |
| 지역 변수 | 축약 금지. `len`/`idx`/`buf` 대신 `frameLength`/`chunkIndex`/`destination` | |
| 부울 | `is`/`has`/`must`로 시작해 문장으로 읽히게 | `mustDropConnection` |

타입명을 짧게, 메서드명을 길게 가져가는 이유: **타입명은 벡터 좌표**(짧고 날카로워야 함)이고
**메서드명은 텍스트 힌트**(길고 서술적이어야 함)이기 때문입니다. 둘의 최적점이 다릅니다.

### 3.0 접미사가 필수인 블록, 생략하는 블록 (시공 중 확정)

접미사는 **동작 블록**(`Fragment` · `Pipeline` · `Index` · `Resource` · `Ledger`)에만 필수입니다.
**데이터 블록**(`record struct`, `enum`, 상수 집합)은 접미사 없이 명사 그 자체로 씁니다 —
`TcpOpcode`, `DropReason`, `ProtocolConstants`.

이유: 접미사의 목적은 "파일을 열지 않고 *실행 성격*을 아는 것"입니다. 순수 함수인가, 가변 상태인가,
진입점인가는 열기 전에 알아야 할 정보지만, `enum TcpOpcode`가 데이터라는 사실은 이름이 이미
말하고 있습니다. `TcpOpcodeRecord`는 정보를 더하지 않고 명사구만 흐립니다 — 황금률 위반입니다.

### 3.1 접미사를 타입명에 남기는 이유

`UdpNonce`가 아니라 `UdpNonceFragment`로 씁니다. 장황해 보이지만,
에이전트가 "이 파일이 순수 함수인지, 가변 상태인지, 진입점인지"를 **파일을 열지 않고**
파일명만으로 알 수 있게 하는 것이 토큰 절약의 핵심입니다. 이진 탐색 디버깅에서
`*Pipeline.cs`만 훑어 검문소를 세우고 `*Fragment.cs`에서 범인을 찾는 워크플로가 이 접미사에
직접 의존합니다.

## 4. 디렉터리 = 도메인, 접미사 = 유형

블록 유형별로 폴더를 나누지 **않습니다**(`Fragments/`, `Pipelines/` 금지).
같은 유즈케이스의 파편·파이프라인·레코드는 **한 폴더에 함께** 둡니다.

```
Wire/
  WireIndex.cs
  ReadTcpFramePipeline.cs
  TcpFrameHeaderRecord.cs
  ParseTcpFrameLengthFragment.cs
  RejectOutOfQuotaFrameFragment.cs
```

이유: RAG의 코사인 유사도는 **도메인 축**에서 결정됩니다. 유형별 폴더는 무관한 도메인의
파편들을 한 좌표로 뭉쳐 벡터를 흐립니다. 유형은 접미사가 이미 표현합니다.

## 5. 파이프라인 작성 규칙

1. **위에서 아래로 한 방향.** 조기 반환(guard) 외의 분기는 최대 1개.
2. 각 단계는 주석 `// 1.` `// 2.` 로 번호를 붙이고, 번호는 **검문소 번호와 일치**시킵니다.
3. 파이프라인은 다른 도메인의 **인덱스를 호출하지 않습니다**(백서 §3.2). 필요한 것은 파편 주입.
4. 파이프라인이 120줄을 넘으면 뒷부분을 **하위 파이프라인**으로 잘라내고 한 단어로 요약합니다.

## 6. 거부(Refusal)는 자가 신고한다 — 원장 규약

원본 엔진은 39개 거부 사유를 파이프라인이 손으로 `RecordDropped(reason)` 호출해 남겼고,
자기 문서가 "모든 거부는 계수된다"고 주장하는 동안 **절반 이상이 실제로는 아무 데도 기록되지
않았습니다**. 손으로 부르는 규약은 부르지 않아도 컴파일되기 때문입니다.

SBA에서는 이것을 **구조로** 막습니다.

> 검증 파편은 `bool`을 반환하지 않는다. **`Verdict` 레코드**를 반환한다.
> `Verdict`는 거부 시 반드시 `DropReason`을 들고 있으며, 사유 없는 거부는 **타입상 만들 수 없다**.
> 파이프라인은 `Verdict`를 위로 전파할 뿐이고, 적립은 인덱스 경계에서 **한 번** 일어난다.

이로써 "거부했는데 아무도 세지 않는" 상태가 컴파일 단계에서 사라집니다. 이것이 백서 §3.5
자가 신고 데이터의 이 도메인용 구현이며, **SBA가 원본 대비 우위를 주장할 수 있는 첫 지점**입니다.

---

## 7. 이진 탐색 디버깅 지원 — 검문소 규약

백서 §4.2를 실제로 쓸 수 있게 하려면 파이프라인 중간 데이터가 **관측 가능**해야 합니다.

- 모든 파이프라인은 `PipelineCheckpointLedger`를 선택적으로 받습니다(기본 `null` = 비용 0).
- 활성화되면 각 단계의 산출 레코드를 단계 번호와 함께 적립합니다.
- 하네스는 `--checkpoints` 로 이를 켜고, 오염이 처음 나타난 단계 번호를 이진 탐색으로 좁힙니다.

레코드가 불변이기 때문에 스냅샷은 **복사가 아니라 참조 보관**으로 충분합니다. 이것이 §3.4
불변 레코드 규약이 디버깅에 되돌려주는 배당금입니다.

## 8. 금지 목록

| 금지 | 이유 |
|------|------|
| `interface` + 단일 구현 | 백서 §2.2 추상화 지상주의 타파. 구현이 하나면 인터페이스는 RAG 블랙홀 |
| 상속 계층 2단 초과 | 파일을 열지 않고는 실제 동작을 알 수 없게 됨 |
| `partial class` | 한 타입이 여러 파일 = 벡터 좌표 분열 |
| 확장 메서드로 로직 숨기기 | 호출부에서 정의부가 안 보임 |
| 파편 안의 `try/catch` | 파편은 순수. 실패는 `Verdict`로 표현 |
| 축약 파일명 (`Utils`, `Helpers`, `Common`, `Misc`) | 요약 불가능 = 황금률 위반 |

**예외 하나**: 진짜로 교체 가능한 확장점(원본의 `ISecuritySuite`)은 인터페이스를 유지합니다.
구현이 둘 이상이고 제3자가 구현하는 것이 설계 의도이기 때문입니다. 백서가 치는 것은
**구현이 하나뿐인 장식용 추상화**이지 다형성 그 자체가 아닙니다.
